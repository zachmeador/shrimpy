The terminal · mockup

A pathfinder for the terminal client and the commands, in the look of the web client's mockup. Nothing here is built.

Every frame is a terminal drawn cell by cell, and it is live: click one and use the keys the client has. Press Ctrl+G in any of them for the list. Off a Mac, the browser keeps Ctrl+N and Ctrl+T for itself.

01One level at a time

At 80 columns the client has the levels it has today: agents and rooms, then what one agent takes part in, then a thread. The arrows move through them: → goes in, and ← comes back out. It takes the whole screen, and the last line is the keys.

A thread, and the same thread turned over with Tab to the session as the agent sees it. The input stays under both.

02Side by side

A wider terminal shows the levels beside each other: two from 96 columns, three from 128. The keys don't change: → goes in, ← goes out, and the bar marks the list the keys are in.

03A busy room

Each agent at work gets its name and its latest step, and Ctrl+O opens them all. Under them the dock keeps to a line for each kind of thing: who is working, and the soonest trigger with a count. /status lists everything that is still going in the thread.

04What is still going

An agent that ends its turn can leave things going: a command in the background, a question to another agent, a trigger. The thread keeps a line for each above the input, with the command that acts on it at its end. Ctrl+O, which opens tool calls, opens a command's last output too.

The thread with the agent that was asked is under observe. It says who waits on it and from where, for as long as the wait is open, and a click on either line goes to the other thread. Where no command can be written, the line under the work names the shell's command that stops a turn.

Whatever wakes an agent with no message of anyone's leaves a line: a trigger that fired, a command that ended, an agent that answered. A thread that a trigger comes to can hold little else, since an agent with nothing to report writes nothing. The agent's view shows the same turns from inside.

An agent is working while anything of its runs, a turn or a command it left in the background, and one mark says both. An agent that only waits on another says so in words, and is idle only when it waits on no one. The commands that end, cancel, pause or start something are listed only while the thread has something for them.

05Finding a key

A key that acts on one thing is named beside that thing. The last line names the keys that move you, and Ctrl+G lists every key. In a thread ← crosses what is typed first, and goes back from its start, and Esc goes back whatever is typed. A slash opens the commands, as it does now.

06Renaming and archiving a thread

Both are commands written in the thread, as /stop and /model are: /rename and a name, and /archive. Neither is posted. An archived thread leaves its list for the row at the foot of it, which → opens.

Open, an archived thread has a tag by its name and nothing else differs. /unarchive brings it back, and so does a message that lands in it.

07Pictures and files

Ctrl+V attaches the picture or the files on the clipboard, and a file dragged onto the terminal is attached in place of its path. Each stands in what is typed as one piece, the way Pi's editor holds a long paste, so the arrows step over it and Backspace takes it out. Sent, the pieces leave the words and go with the message.

A terminal that speaks Kitty's or iTerm2's picture protocol, which pi-tui draws, shows a picture in the thread and in the agent's view. Anywhere else a picture is its name and size, and the agent's view names its kind, as it does today. A click opens either in the machine's own viewer.

08An agent's page

An agent's list holds only conversations, in two tabs that Tab switches: chat is your DM with the agent, and observe is everything else it takes part in. Its name is the list's first row, and → opens its page: how the agent stands, where it runs, its triggers and its home. Where there is room, the page stands beside the list while no thread is open.

At 80 columns the page takes the screen, as a thread does. On it the arrows move through what it lists: → on a trigger opens the thread it comes to, → on a folder of the home opens it in place, or a file where the page was, and ← goes back.

While a command of the agent's runs in the background, the page lists it above the triggers, and → on it opens the thread that started it.

In observe a thread says where it is: a room, or a DM with another agent. Every row is a thread. A thread opens its agent's list on the tab that holds it. An agent the gateway turned away for its release says so on its page, and what to update.

09When things are not fine

A view with no connection goes dim under its note, a thread you only read says so where the input would be, and with no gateway the first screen is how to start one. The notes about a lost connection and a missing gateway are the terminal's sentences as they are today. The others are the shorter ones from the web mockup.

On a machine whose Shrimpy is older than the gateway's, the first screen says so. /update, written in any thread, leaves the screen, runs shrimpy update with the gateway's version and opens the terminal again on it. After a release that changes the Pi packages or the major, the gateway turns the terminal away and no thread opens, so the first screen offers the same update, and Enter starts it. A page comes from the gateway, so it has none of this.

10On the terminal's own colors

Where a terminal has no true color, the client paints no ground: it draws on the terminal's own, in its sixteen colors. The layout and the marks are the same.

11The commands

The commands print plain lines and tables, which agents read, and those stay as they are. On a terminal that shows color, three things are added: a name or a command to run is bold, a state has a color, and what failed is red.

12What it is made of

The web client's stitch is two pixels. Here it is the cell, and the dot of a braille cell. A sigil is written once, as twelve lines of twelve, and each client draws it its own way.

The same colors, by name

The tokens are the web mockup's. A word uses the form that is safe for small text, and a mark uses the brighter one.

    The 3.0 harness, drawn on 2026-11-26 from its plan, BRANCH-PLAN.md in git at 33e5aaa9, and not built

    • Every row of a list is a thread, as in the web mockup, whose notes say what was chosen for what is drawn in both. A trigger that wakes its agent comes to a thread, so a trigger's own session is gone from observe.
    • What is still going between turns is a line for each kind above the input: ▪ a command in the background, ○ the agents waited on, ◷ the soonest trigger. Each ends with the command that acts on it: /kill, /cancel, /pause or /resume, and /drop for an agent that isn't running. All five are listed only while the thread has something for them. Several of a kind are the first and a count, and /status lists them all.
    • Ctrl+O opens a command's last output, under its line and on the agent's page, and what a line in the thread brought. Until now a trigger's line always showed what it brought, which a thread of little but such lines can't.
    • One mark, ▪, for whatever runs: a turn, or a command the agent left in the background, and the row says working for both. A tool call that runs has it too, where it had ●, as the web mockup has one lantern for both. An agent that only waits on another has none, and its row says whom it waits on. A row has no clock for a trigger. The web mockup's notes say why.
    • Whatever wakes an agent leaves a line, and lines that follow each other stand together, as a log does.
    • A click on "waiting on" opens the thread with that agent, and a click on the line there goes back. No key does either, since the lists reach both threads. That thread says who waits on it only while the wait is open, since only open waits are listed.
    • /drop stops waiting on an agent, and nothing a click can reach does, so a wait isn't dropped by a slip. The line names it for an agent that isn't running, whose wait ends no other way. It leaves no line and tells the agent nothing, as cancelling and pausing a trigger do in the plan.
    • A thread you only read names the shell's command that stops a turn, shrimpy sessions stop, where the web mockup has a button.
    • On an agent's page → on a command in the background or a trigger opens its thread, and on a trigger that only leaves a note, the note. Nothing on the page ends a command or turns a trigger off: its thread's commands do, and for a trigger with no thread, shrimpy triggers off in a shell.
    • /stop ends a turn and nothing else, and a note says once what is still going.

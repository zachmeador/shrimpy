# 🦐 Clients Scout

Originally researched: 2026-11-11
Status: Research; nothing adopted, installed or run

The question: what can Shrimpy's web client, one frontend for a phone and a desk, and the companion app that later wraps it copy or only study from open-source agent apps, chat apps and UI kits, and how does the owner reach Shrimpy from a phone?

Research agents read public sources and code on 2026-11-11, and a second pass rechecked 16 claims per topic against primary sources and corrected those that held only in part. The GooeyPi review is from 2026-08-13. Statements were read in the primary source linked here or under [Sources](#sources) unless marked **(I)** for the research's inference or **(S)** for a secondary source, such as a press report or a search summary.

**Copyable** means MIT, Apache-2.0 (keeping its NOTICE), BSD or ISC, with each copyright and permission notice kept. Anything else, a reworded license included, is **study only**. Licenses were read in each repo; transitive dependencies, Orca's `cloud/`, Paradev's relay and hosted relays' terms weren't checked. Versions, stars, author counts and activity are as of 2026-11-11.

## Current recommendation

**Fork none of the agent-session apps, and borrow by layer.** **(I)** Nearly every active app that manages agent sessions is built around repositories and worktrees, or around one coding session, and forking one would bring a second owner of sessions alongside Shrimpy's agents.

- **The phone gets the installed web app, as the plan has it.** With trusted HTTPS, Web Push reaches an iPhone Home Screen app with no store, no fee and no relay of Shrimpy's own. **(I)** What such an app can't do on iOS, such as replying from a notification or replacing an alert, is the case for a companion app later. That app needs native push: through a relay the project runs or rents for an App Store build, or with the owner's own key for Apple's push service (APNs) on the gateway for a build the owner signs, as OpenClaw's self-built app does.
- **Build the web client in React, from parts (I):** assistant-ui's runtime adapters, which connect its components to a custom backend; shadcn/ui's AI Elements, restyled from the owner's mockups; Streamdown, which renders Markdown safely as it streams; and a virtualized list. Every mature agent-chat kit found is React.
- **Desktop.** The plan has no desktop app: on a desk the web client lays itself out side by side, and a desktop chat app is deferred ([PLAN.md](../REDESIGN/PLAN.md#direction)). **(I)** If a wrapper's tray, shortcuts or deep links are missed, Electron fits, hardened as GooeyPi's is. Tauri is worth another look once its build on CEF (the Chromium Embedded Framework, in place of the system WebView) is stable.
- **Where to look, by layer (I):**
  - One frontend shipped as a web app, in Electron and in Capacitor: OpenChamber.
  - A Pi Durable web client's transport, cache and Web Push: Pi Pocket.
  - Server-owned sessions, device pairing, and connection routes tried in a set order: T3 Code.
  - Phone push and pairing: Collie and Ovis.
  - Sign-in code: Chord v2, the experimental runtime of Pi's library for apps across processes, and p2, Earendil's prototype web app.
  - Long-lived agents with many conversations: OpenClaw and Hermes.
  - Rooms where several agents answer: Hermes Group Chats and Nuphos.
  - Push without message text: OpenClaw.
  - Channels and topics: Zulip.
- **Sign-in (I):** a hashed session per browser or phone, which a browser holds in a signed HttpOnly cookie and a wrapper's native code sends as a bearer token. The rules to copy are [below](#sign-in-rules-from-the-strongest-apps).
- **If agents drive Claude Code or Codex (I),** those sessions draw in the same session view, from Shrimpy-owned shapes, and open like any of the agent's sessions. The plan keeps Codex as a worker and has no Claude Code; the rest is the [coding-agents note](coding-agents-scout-2026-11-11.md)'s proposal ([below](#claude-code-and-codex-in-the-client)).
- **The wire under the web client is open** ([below](#the-wire-under-the-web-client-is-open)). **(I)** Components, push, pairing and what sign-in must do can be chosen now. The code that talks to the gateway, and whose sign-in code it is, follow the wire.

What the research would do next **(I)**:

1. Once the owner answers the questions on the entry, invitations and certificates, give the gateway's entry HTTPS, which installing and push both need, and a session per device.
2. Show the owner mockups of the one frontend before any screen is built, as [using-it.md](../REDESIGN/design/using-it.md) has it, weighing GooeyPi's desk-width arrangement and Zulip's topics.
3. Test on an iPhone and an Android phone: whether a pairing made in Safari carries into the Home Screen app (leave an HttpOnly cookie and an IndexedDB value in Safari, then install and check both); `SameSite=Strict` against `Lax` on notification taps and installed launches; delivery after a force-quit and after a reboot; and a new WebSocket after a resume, over the tailnet name ([WebKit 308073](https://bugs.webkit.org/show_bug.cgi?id=308073)).
4. Compare OpenChamber, Pi Pocket, Collie and Ovis in code on push, pairing, transport, offline cache and wrapper bridge, including whose relay sends to OpenChamber's Capacitor app.
5. Read what p3, the app Earendil plans as p2's successor, decides about Chord's app kit in the week of 2026-11-16, before the code that talks to the gateway is written.

## The wire under the web client is open

Pi 1.2.0 (2026-10-12) removed `pi-client`, `pi-server` and `pi-protocol` ([pi-agent.md](pi-agent.md#upstream-after-100)), which [2-contracts.md](../REDESIGN/design/2-contracts.md) names as the transport for every client, with a "small WebSocket bridge" for the web client.

- Chord 1.2.0 removed the service runtime Shrimpy's contracts are written in, so moving `pi-durable` past 1.1.0 means a new wire for all three programs **(I)**.
- p2 runs on Chord v2, which is marked experimental and has been Chord's main entry since 1.5.1 (2026-11-09).
- Durable 1.5 sends a window of the newest entries, which `ConversationTranscript` pages on the client.
- Shrimpy's browser entry listens on loopback, refuses pages of other origins and authenticates nothing ([web.ts](../../src/gateway/web/web.ts), [origin.ts](../../src/gateway/web/origin.ts)).

The options are in [pi-agent.md](pi-agent.md#options-for-shrimpys-wire), and the choice is the first question [for the owner](#for-the-owner).

## How OpenClaw and Hermes reach their owner

Of the home-agent frameworks checked, only these two model long-lived agents with many conversations, and both put the trust boundary at the gateway, as Shrimpy does. nanobot, ZeroClaw and IronClaw serve web UIs from their gateways, and their READMEs show nothing to borrow beyond OpenClaw's **(I)**.

**[OpenClaw](https://github.com/openclaw/openclaw)** serves a Vite and Solid Control UI from the gateway and ships Swift apps for iOS and macOS and a Kotlin app for Android. It is MIT and copyable, though its code leans on its own config. v2026.11.3 came out on 2026-11-10, and the project has about 3,784 contributors.

- **Sign-in:** the first connect carries the gateway's token or password, the client's Ed25519 identity signs a challenge, the owner approves a `PAIRING_REQUIRED` request, and the client keeps a device token ([clients.md](https://github.com/openclaw/openclaw/blob/main/docs/gateway/clients.md)).
- **Push:** the Control UI gets Web Push through its service worker, subscriptions bind to the paired device, and excerpts, prompts and command arguments never enter a payload ([notifications.md](https://github.com/openclaw/openclaw/blob/main/docs/web/notifications.md)).
- **Reach:** loopback port 18789 by default; phones come over the LAN, a tailnet or SSH, and the docs recommend Tailscale Serve for HTTPS. The labs feature "OpenClaw ID" adds a relay built on iroh, a library for direct connections between devices, with owner-signed invitations, so far for headless nodes ([remote.md](https://github.com/openclaw/openclaw/blob/main/docs/gateway/remote.md)).
- **iOS:** pairs by QR or code. A self-built app needs the owner's APNs key on the gateway. App Store builds use a hosted relay that holds the APNs credentials and, through App Attest, grants a send scoped to one paired gateway ([iOS README](https://github.com/openclaw/openclaw/blob/main/apps/ios/README.md), [ios.md](https://github.com/openclaw/openclaw/blob/HEAD/docs/platforms/ios.md)).
- **Agents:** isolated agents per gateway, bound to channel accounts, whose sessions can message each other ([multi-agent.md](https://github.com/openclaw/openclaw/blob/main/docs/concepts/multi-agent.md)).

**[Hermes Agent](https://github.com/NousResearch/hermes-agent)** (MIT; copyable, but Python, so ideas; v0.23.1 on 2026-11-10) runs one React renderer in Electron and in browsers, and its transcript uses `@assistant-ui/react`.

- v0.23.0 serves the Desktop workspace to browsers as the "Webapp": off by default, single-user, behind sign-in, with a CSP and opt-in notifications ([release](https://github.com/NousResearch/hermes-agent/releases/tag/v0.23.0)). One gateway per machine owns its conversations, and Desktop connects to several.
- Group Chats seat bots from several machines. A lead bot or router picks who answers an unaddressed message, only when opted in.
- There is no official phone app; community clients weren't read.

**(I)** What the two mean for Shrimpy:

- Hermes is a working case of one responsive frontend, served to browsers and wrapped in Electron.
- Of OpenClaw's phone app, Shrimpy's design calls for the chat and notifications half, not its device control.
- Nuphos and Hermes Group Chats are precedents for rooms where several agents answer, though Hermes's router that picks who answers is what Shrimpy leaves to each agent's wake policy. OpenClaw's [multi-user mode](https://github.com/openclaw/openclaw/blob/main/docs/concepts/multi-user.md) isn't one, since a Shrimpy gateway has one person.
- No app read lets the owner open a DM between two agents; OpenClaw and Hermes weren't checked for it.

## Pieces to borrow

Each piece is borrowed for what it does. How the client looks and is laid out comes from the owner's mockups ([using-it.md](../REDESIGN/design/using-it.md)).

### Window shell and its hardening

GooeyPi is the reference for an Electron shell **(I)**. A review of its source at commit `cd5e060` (2026-08-13), before v1.1.21 and not repeated since, found:

- A sandboxed renderer with no Node, context isolation, a strict CSP and one exact renderer URL.
- A frozen preload API, with every call rechecked by the main process against the authorized frame and URL.
- Remote pages in their own partition, with no preload.
- Release gates for Electron fuses, ASAR contents and native-unpack allowlists, signing, notarization, checksums and size budgets.
- Rules for driving a harness over stdio, which belong to whichever program drives Codex or Claude Code **(I)** and are in the [coding-agents note](coding-agents-scout-2026-11-11.md#design-7s-codex-workflow-and-what-a-restart-does).

T3 Code adds a rule: native modules stay off Electron's main-process startup path. For the owner's mockups, GooeyPi's desk-width arrangement is one to weigh: an agent and session sidebar, the transcript, a floating composer, a side inspector, a bottom terminal drawer and a command palette.

### Transcripts and long sessions

- **Take these libraries as they are (I).** [Streamdown](#composer-and-tool-calls) renders Markdown safely mid-stream. `@legendapp/list` 3.7.2 (MIT; copyable) is OpenChamber's chat list, patched for scrolling. `@pierre/diffs` 1.6.4 (Apache-2.0; copyable), in 14 of the coding apps checked, could draw an `edit` tool call in a session view.
- Cinny uses TanStack Virtual for the job `@legendapp/list` does. Vercel's AI Elements package depends on Shiki for code and `use-stick-to-bottom` for scroll anchoring.
- **Long sessions on a phone.** p2's numbers through ngrok, and p3's rules in answer, are in [pi-agent.md](pi-agent.md#earendils-own-apps) and [efficiency.md](https://github.com/earendil-works/pi/blob/main/apps/p3/docs/efficiency.md). After one 6,000-entry session became an 8 to 10 MB event, Pi Pocket sends the newest 80 rows first, sends light entries, and on reconnect sends only what a tab lacks.
- **`ConversationTranscript`** (MIT; copyable; about 12.5 KB) keeps a client's transcript across Durable's windows and reconnects, marks gaps and pages back ([Durable README](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md)). **(I)** Using it in a Shrimpy client ties the client to Durable's record types, against "Contracts carry Shrimpy-owned shapes only" in [2-contracts.md](../REDESIGN/design/2-contracts.md). The alternative is a session view that pages itself, borrowing its logic.

### Session lists

- **What the list holds.** An agent's screen in the terminal is one list of everything it is part of: its DMs with the owner and with other agents, the rooms it has worked in and its triggers' own sessions, newest first, narrowed to the owner's threads and back ([using-it.md](../REDESIGN/design/using-it.md)). The web client's list would start there **(I)**; the apps below list one user's sessions with one assistant.
- OpenChamber shows which sessions are working, waiting, finished or failed, with approvals, scheduled tasks, provider limits, tokens and cost. [Sheprd's](https://github.com/sheprd-labs/sheprd) (Apache-2.0; copyable) daemon owns a status dot: idle, working or waiting on you.
- T3 Code settles a thread's outcome on the server and clients render it, and a client viewing one thread doesn't pay for every thread's history ([overview](https://github.com/pingdotgg/t3code/blob/HEAD/docs/internals/overview.md)).
- **(I)** Shrimpy has no state for a session waiting on the owner: an agent that needs the owner writes in the thread, and the thread marks what came while the owner was away ([using-it.md](../REDESIGN/design/using-it.md)). A list shows work from who is working, which the chat server keeps with each thread ([4-conversation.md](../REDESIGN/design/4-conversation.md)), and from each agent's sessions. A "waiting on you" state would come with the approvals in the [coding-agents note](coding-agents-scout-2026-11-11.md#for-the-owner), and is the owner's call there.
- Watching several sessions at once: Nuphos splits panes with ⌘D, Orca splits "anything", and OpenChamber's desktop has several windows and a Mini Chat.

## The phone path

### An installed web app with Web Push

- **iOS and iPadOS 16.4 and later** deliver Web Push only to Home Screen web apps, with permission asked on a tap. Push goes through APNs, needs no Apple Developer Program membership, and can set the app's badge ([WebKit](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)). From iOS 26, a site added to the Home Screen opens as a web app by default.
- **Declarative Web Push** (iOS 18.4 and later) shows a JSON payload with a title and a URL without a service worker, even after one is removed ([WebKit](https://webkit.org/blog/16535/meet-declarative-web-push/)).
- **Every push must show.** WebKit drops a subscription after three silent pushes, and Chromium allows a fully engaged site about six silent pushes a day ([`budget_database.cc`](https://github.com/chromium/chromium/blob/main/chrome/browser/push_messaging/budget_database.cc)), so Collie caps the pushes that only retract an alert at four per phone a day ([Collie](https://github.com/AltanS/collie/blob/HEAD/docs/voice-and-push.md)). **(I)** Ration pushes that only retract or badge.
- **(I) A setup can send push with no service of the project's:** a VAPID keypair, which identifies the sender to push services, stored subscriptions and outbound POSTs, with no inbound port and no Apple or Google account, since the browser picks the push service and the payload is encrypted for that browser ([web.dev](https://web.dev/articles/push-notifications-how-push-works)). Pi Pocket's [`push.ts`](https://github.com/TannerMidd/pi-pocket/blob/main/src/server/push.ts) does it with Node built-ins. Which program sends it is open. The gateway never holds conversations ([1-programs.md](../REDESIGN/design/1-programs.md)), and the chat server keeps what was said, who is working in each thread and where each person was last active ([4-conversation.md](../REDESIGN/design/4-conversation.md)), while the devices a subscription belongs to would be signed in at the gateway.
- [Collie](https://github.com/AltanS/collie) skips devices that are showing the app, and OpenClaw keeps message text out of payloads. **(I)** Both fit "a push notification when an agent answers or writes while you are away" in [using-it.md](../REDESIGN/design/using-it.md).
- **Risks.** iOS 17.4 betas removed Home Screen web apps in the EU, and Apple restored them, WebKit-only, in March 2024, per [Notebookcheck](https://www.notebookcheck.net/Apple-backpedals-on-decision-to-kill-Home-Screen-web-apps-in-EU.809180.0.html) **(S)**; no 2026 change was found. No source says whether iOS delivers to a force-quit Home Screen app. It probably does, since a system service, `webpushd`, shows the alerts **(I)**.

### What an installed iOS web app can and can't do

Checked against iOS 27.2, with 27.3 in beta. No Safari release note or WebKit post checked from 26.0 on changes notification buttons, tags, badges, sharing, link handling or push in web views; 26.0 made any site saved to the Home Screen a web app, and 26.2 fixed how Declarative Web Push reads `mutable`.

| Web Push | From 16.4 | From Chrome 42 |
| Buttons on a notification | No | Two, from Chrome 48 |
| Inline reply | No | On by default since Chrome 68; untested |
| A new alert replaces one with the same `tag` | No ([319860](https://bugs.webkit.org/show_bug.cgi?id=319860), open) | Yes |

| Camera | Asked again at each cold start ([215884](https://bugs.webkit.org/show_bug.cgi?id=215884); follow-up [327237](https://bugs.webkit.org/show_bug.cgi?id=327237), open, on iOS 26.6.2) | Yes |
| `BarcodeDetector` | Behind a flag | From Chrome 83 |

**(I)** The web app is enough if answering an agent from an iPhone may take four steps: unlock, tap, reconnect ("a few seconds" over Ovis's relay), then reply. Nobody has measured what the extra steps cost.

- **Buttons on a notification.** Shrimpy's design has no approval prompt for an agent's work: an agent that needs the owner asks in the thread, and the answer is a reply ([7-on-its-own.md](../REDESIGN/design/7-on-its-own.md)). Approvals would come only with the [coding-agents note](coding-agents-scout-2026-11-11.md#for-the-owner)'s proposal that a Codex or Claude Code session's approvals reach the owner. For that case, [Ovis](https://github.com/devswha/ovis/pull/2939) shows buttons only for one or two options of at most 24 characters, on a prompt within 4 lines and 300 characters, and only on devices allowed to answer; a tap on a prompt that has moved on gets `409 prompt_changed`. Pi Pocket offers Allow only when the whole call shows. Only a native app can require an unlock before Allow ([Ovis #2916](https://github.com/devswha/ovis/issues/2916)), so a web app's Allow may answer from a locked phone **(I)**. **(I)** If approvals come, send one payload for both platforms: buttons, plus a URL to the approval card, with no "tap Allow" in the text.
- **Pairing.** Collie has phones type its code into the installed app "because the camera opens the QR code in a browser tab" ([security.md](https://github.com/AltanS/collie/blob/HEAD/docs/security.md)). Whether a pairing made in Safari carries into the Home Screen app is disputed: Collie says no, Ovis implies yes, and nobody tested it. **(I)** The invitation would be a short code typed inside the installed app, valid for minutes with few tries, and the app would take a pasted link too, as Pi Pocket's does. A link opened in Safari would show the code and the steps instead of spending it. A scan inside the app needs a JavaScript decoder, such as [zxing-js](https://github.com/zxing-js/library) (Apache-2.0; copyable; v0.23.0 on 2026-04-29).
- **Storage.** Safari's deletion of script storage after seven days without a visit doesn't reach Home Screen apps ([WebKit](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/)). Re-adding the icon means new storage and a new push subscription. Collie's service worker once served every navigation from its precache, hiding a sign-in proxy's page, and a 401 looked like an outage ([#31](https://github.com/AltanS/collie/issues/31)). **(I)** Never serve sign-in routes from the cache, and tell a 401 from an outage.
- **Catch-up.** In WebKit bug [308073](https://bugs.webkit.org/show_bug.cgi?id=308073) (iOS 26.3, open), a new WebSocket after a resume hangs in CONNECTING while `fetch()` works; it was reported for `ws://` to a LAN IP. **(I)** Treat going to the background as a disconnect: on `visibilitychange`, reconnect, fetch what came after a per-thread cursor and draw the cached thread first, as Pi Pocket does. Connect by host name. An event-stream or long-poll fallback would be the plain HTTP entry the plan defers until a program that can't speak Pi's protocol needs in ([2-contracts.md](../REDESIGN/design/2-contracts.md)); a page on iOS whose new WebSocket hangs may be that program, which is the owner's call.
- **Subscriptions die unseen.** iOS fires no `pushsubscriptionchange` ([273063](https://bugs.webkit.org/show_bug.cgi?id=273063)). Collie retires an endpoint after 5 straight failures while a sibling on the same push service succeeds ([#69](https://github.com/AltanS/collie/pull/69)), and Ovis offers "Turn alerts on again". **(I)** Treat a subscription as soft state, check it on each open, and show push health.

### HTTPS without requiring Tailscale

- **A phone needs a secure context.** At `http://100.101.102.103:7447` a page gets no service worker, Push, `crypto.subtle` or passkeys, though iOS 26 still adds it to the Home Screen ([MDN](https://developer.mozilla.org/en-US/docs/Web/Security/Secure_Contexts/features_restricted_to_secure_contexts)).
- **`tailscale cert`** gets Let's Encrypt certificates for `machine.<tailnet>.ts.net`, with keys kept local. It needs MagicDNS and HTTPS switched on, publishes each certified name in Certificate Transparency logs, and leaves the 90-day renewal to the user ([Tailscale](https://tailscale.com/kb/1153/enabling-https)).
- **Let's Encrypt DNS-01**, its automatic check through DNS, covers private names and wildcards, needs a DNS provider with an API, can't validate IP addresses, and advises scoped DNS tokens ([challenge types](https://letsencrypt.org/docs/challenge-types/)). Lifetimes fall to at most 45 days by February 2028.
- **A local CA** (mkcert, Caddy's) needs its root on each phone, with full trust switched on in iOS. Android apps must opt in to user roots, though Chrome trusts them **(S)**.
- **A public tunnel.** Agent Orchestrator tries a Cloudflare quick tunnel alongside LAN and Tailscale, preferring it last, because its certificate satisfies iOS App Transport Security, and its [ADR 0004](https://github.com/OrchestratorInc/agent-orchestrator/blob/HEAD/docs/adr/0004-cloudflare-tunnel-for-remote-mobile-access.md) records that TLS ends at Cloudflare, "not end to end". Shrimpy doesn't count on any proxy in front of its entry ([6-network.md](../REDESIGN/design/6-network.md)), so a tunnel isn't one of its routes **(I)**.
- **(I)** The gateway's entry would terminate TLS itself, since Shrimpy serves its own entry with no proxy in front. That ends "None of Shrimpy's own for now", the Encryption row of [6-network.md](../REDESIGN/design/6-network.md), where a phone comes in, as [using-it.md](../REDESIGN/design/using-it.md) foresees: installing and push need HTTPS, and how the gateway gets a certificate is to settle. The entry could load a certificate and key from files: those `tailscale cert` writes, those an ACME client writes after DNS-01 for the owner's domain, a local CA's, or a pair the owner supplies, with an agent getting and renewing them by a skill. DNS-01 is the one automatic route that needs neither Tailscale nor a third party in the data path. Loading what `tailscale cert` writes fits [the design's Tailscale rule](../REDESIGN/design/6-network.md), since switching on MagicDNS and HTTPS stays Tailscale's own business.

### When a companion app is worth it, and the relay it needs

- **Home Assistant's** Apple app is a WKWebView showing HA's frontend, joined to native code by a JavaScript message bus with "external authentication", so people sign in once ([architecture](https://contributors.home-assistant.io/companion/apple/architecture/)). It pushes over the app's WebSocket while connected and otherwise through a relay. The official relay sends through Google's push service (FCM) to both platforms, 500 a day per device by default, and its code is offered as a starting point ([notifications](https://contributors.home-assistant.io/companion/mobile-app-api/notifications/)).
- **Web views have no Push API.** Neither WKWebView nor Android WebView has the Push or Notifications API, and without an entitlement WKWebView runs service workers only on App-Bound Domains, at most 10 and fixed in `Info.plist` ([WebKit](https://webkit.org/blog/10882/app-bound-domains/)).
- **A mismatch with the plan (I).** [The plan](../REDESIGN/PLAN.md#direction) has the companion app wrap "the same pages", as Home Assistant's does. On iOS that can't bring Web Push along: WKWebView has no Push API, and a store app can't list every owner's gateway as an App-Bound Domain to run its service worker. So the companion needs native push. From the App Store that goes through a relay the project runs or rents, which holds the APNs key, as Home Assistant runs one for its app. A companion the owner builds and signs could send with the owner's own APNs key on the gateway, as OpenClaw's self-built app does, at Apple's yearly fee. The plan says neither.
- **The rule for notifications (I).** The owner agreed, for the companion's sake, that what sends a notification doesn't know whether a browser or an app receives it ([using-it.md](../REDESIGN/design/using-it.md)). That holds only if one sender hands each subscription to Web Push or to the relay.
- **OpenChamber's Capacitor app** takes native push through `@capacitor/push-notifications` in its [mobile package](https://github.com/openchamber/openchamber/blob/HEAD/packages/mobile/package.json); whose relay sends to it wasn't read.
- **Android (I):** a [Trusted Web Activity](https://developer.android.com/develop/ui/views/layout/webapps/trusted-web-activities) runs in Chrome and keeps Web Push, while a WebView companion needs FCM and a relay. Whether one published app can be verified, through Digital Asset Links, against any owner's gateway is unknown. Links into a native app need verified Universal Links on iOS and App Links on Android ([Ovis #2599](https://github.com/devswha/ovis/issues/2599)), so a store app faces the same question for every owner's gateway.
- **Relay designs:** Happy's push worker treats an unguessable token as the capability, so self-hosted servers need no credentials ([README](https://github.com/slopus/happy/blob/HEAD/packages/happy-push-server/README.md)); OpenClaw's grants a send scoped to one paired gateway.
- **Costs:** Apple's program is "99 USD per membership year" ([Apple](https://developer.apple.com/programs/enroll/)). Google Play is $25 once, and new personal accounts need a 14-day closed test with 12 testers. Android developer verification began on 2026-09-30 for installs from participating stores in Brazil, Indonesia, Singapore and Thailand, and reaches all apps on certified devices in 2027; hobbyists may share with 20 devices without ID or fee ([Android](https://developer.android.com/developer-verification)).
- **(I) A companion is worth it for any of these:**
  - answering from the notification, with an unlock required first;
  - links or QR codes that open the app;
  - receiving shares;
  - alerts reliably replaced or cleared;
  - camera or microphone permission that survives a relaunch;
  - Live Activities, widgets or the Watch.

  The order the research would take: the installed web app, then Android's notification buttons, then the iOS companion once those gains outweigh a relay and the fee. Ovis, a hosted web app, has added native apps that get alerts through its own APNs relay ([#1695](https://github.com/devswha/ovis/pull/1695), [#1817](https://github.com/devswha/ovis/pull/1817), titles only). Collie and Pi Pocket stay on the web.

### Phone apps for coding agents and how they connect

They connect four ways:

- an end-to-end encrypted relay, usually self-hostable (Happy, Paseo, Ovis), or run by the publisher, as [OpenChamber's Private Relay](https://github.com/openchamber/openchamber/blob/HEAD/packages/docs/content/docs/private-relay.mdx) is: the server dials out, device and server agree keys directly, and the relay forwards sealed traffic to devices paired once;
- a hosted account service (T3 Connect, Orca Relay);
- a direct LAN, tailnet or SSH path, which all of them offer;
- a public tunnel (Agent Orchestrator, Maestro).

Push almost always goes through the publisher's relay or the push service of Expo, a React Native toolkit. The self-hosted web apps use Web Push.

- **The credential.** T3 Code, Chord, p2, OpenChamber and OpenClaw keep one hashed or signed session per device. Chord's token is `<id>.<secret>`, storing only the secret's SHA-256, carried in a signed `chord-session` cookie that is always `SameSite=Strict`, HttpOnly, and `Secure` when remote. p2's cookie is `SameSite=Lax`, so cross-site links arrive signed in. OpenClaw keeps a raw Ed25519 key and its device token in localStorage. **(I)** Only an HttpOnly cookie is beyond page script.
- **Cookies ignore ports** ([RFC 6265 §8.5](https://www.rfc-editor.org/rfc/rfc6265#section-8.5)): a cookie for `127.0.0.1` reaches every local port, other accounts' servers included, as p2 warns.
- **Socket tickets.** A socket ticket is a short-lived token a page presents when it opens a WebSocket, since a browser page can't set an `Authorization` header on a WebSocket, only send its cookies and a subprotocol list. T3 Code's last 5 minutes and are bound to a use, such as `rpc`; OpenChamber's last 60 seconds; both can be reused until they expire. Hermes's browser tickets are one-use and last 30 seconds, though its loopback dashboard still puts a token that lasts until restart in `?token=`. OWASP prefers a token in the first message over WSS, since query strings leak into logs ([cheat sheet](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html)).
- **Chord's request rules,** built from p2's:
  - Local means a loopback socket, and a `Host` with the port and no forwarded headers.
  - Any other `Host` must be listed, and counts as `https://`.
  - WebSocket upgrades refuse a foreign `Origin`. Routes marked `crossSite` skip the `Origin` check and run anonymous.
  - A `Sec-Fetch-Site` other than `same-origin` or `none` is never authenticated, except on a top-level page `GET`.
  - Anonymous calls to routes that aren't public get 401 before any handler runs.
  - Responses carry `no-store`, `nosniff`, `no-referrer`, `X-Frame-Options: DENY` and a nonce CSP by default, which contributed framers, CSP sources and route headers can widen.
- **LAN and tailnet addresses split the apps.** Hermes treats private, CGNAT (the `100.64.0.0/10` range tailnets use) and link-local addresses as public and turns on its sign-in gate. OpenClaw accepts an `Origin` that matches a private-IP, `.local` or `.ts.net` `Host`. T3 Code and OpenChamber accept an `Origin` that matches `Host`, which doesn't stop DNS rebinding **(I)**. T3 Code is covered because every route needs a credential. OpenChamber's passwordless loopback default may not be (untested). It refuses `Origin: null` and LAN binds without a password, but its [`request-security.js`](https://github.com/openchamber/openchamber/blob/3ab79b837566f26d9df67728c9aaf69013f1bb0c/packages/web/server/lib/security/request-security.js) needs a `Host` allowlist before it is borrowed.
- **ClawJacked** ([Oasis Security](https://www.oasis.security/blog/openclaw-vulnerability), 2026-02-26): a web page brute-forced OpenClaw's loopback password, since loopback was exempt from rate limits, and was paired automatically. OpenClaw now throttles loopback per `Origin` and never silently pairs browser origins other than its own UIs.
- **Pairing.** Link secrets ride in the URL fragment and are stripped and POSTed to the same origin (Chord, p2, OpenClaw, Hermes, T3 Code). Chord's device codes are `XXXX-XXXX` with no look-alike characters, last 10 minutes, need the owner's approval, and are capped at 100 pending and 10 per address: the shape of Shrimpy's `K7Q2-9FXD`, though Chord's run the other way, a device asking and the owner approving, which [6-network.md](../REDESIGN/design/6-network.md) turned down since it would open the gateway to strangers. OpenClaw warns that a code isn't a secret, so its owner checks the Browser ID before approving. p2's local clients answer an HMAC challenge, since loopback alone proves nothing on a shared machine. Pi Pocket's reusable `GET /login?token=` is the pattern to avoid **(I)**.
- **Revocation and scopes.** T3 Code, Chord, p2, OpenChamber and OpenClaw revoke devices one at a time, and p2, OpenClaw and Hermes also close live sockets. Only T3 Code (16 scopes, narrowed at exchange) and OpenClaw (capped by role) have scopes.
- **Wrappers.** p2-mac signs in through a `URLSession` with no cookies and injects the HttpOnly cookie into one `WKWebsiteDataStore` per server. OpenChamber trusts `capacitor://localhost` and `https://localhost` by name; leaving out the Android origin once broke every WebSocket while SSE kept working. **(I)** Serving the web app, the installed app and a wrapper from the gateway's origin keeps one cookie; a wrapper on its own scheme needs a bearer and a listed origin.

What the research would do **(I)**:

- One device row per browser or phone, shaped like Chord's `Sessions`. A browser holds its token in a signed HttpOnly cookie (`Secure`, with a `__Host-` name on HTTPS), and a wrapper's native code sends it as a bearer token. The owner's machines and agents keep the token they make for themselves, whose hash the gateway keeps ([6-network.md](../REDESIGN/design/6-network.md)).
- Socket tickets that are single-use, minutes long and bound to a route and a session, close to Shrimpy's [tickets](../REDESIGN/PLAN.md#words), which are single-use, short-lived and good for one program. Shrimpy's entry carries its ticket in the URL's query today (`?ticket=`, [endpoint.ts](../../src/contracts/gateway/endpoint.ts)); OWASP's way would move it into the first message.
- Chord's request rules, HTTPS for other devices, an exact `Origin` (the gateway's own or a listed wrapper's), and throttling per address and per loopback `Origin`. Scopes can wait.
- The local page's secret proven by a 0600 file, an HMAC challenge or, on Linux, a peer-UID check as Hermes does, never by loopback alone.
- Revocation that closes sockets. Nothing takes a machine's token back at the gateway yet ([6-network.md](../REDESIGN/design/6-network.md)), and replacing a token isn't designed ([3-identity.md](../REDESIGN/design/3-identity.md)), so this would be the first revocation.
- Neither stored bearer tokens, which XSS can copy and Safari wipes after 7 days without a visit outside Home Screen apps, nor device keys, which need HTTPS and whose DPoP proofs of possession need replay records.

Where this meets the design **(I)**:

- [6-network.md](../REDESIGN/design/6-network.md) refuses at the entry on a listen address "a connection that says it comes from a web page", and serves no files there. The browser entry that serves the web client listens on loopback only and admits only pages of its own origin, `http://127.0.0.1:<port>` or `http://localhost:<port>` ([origin.ts](../../src/gateway/web/origin.ts)). A phone needs the files and a way in at an address it reaches, so one of the two entries changes.
- [using-it.md](../REDESIGN/design/using-it.md) has a phone come in "as a machine of your own does". A machine makes its token and keeps it in its folder; a browser's would be made by the gateway and set as a cookie, so that page script never holds it.
- [3-identity.md](../REDESIGN/design/3-identity.md) lets the page on the gateway's machine in "with a link that carries a secret only that OS user can read". A cookie the page then holds for `127.0.0.1` reaches other accounts' servers on other ports. Hermes's per-tab handoff avoids that, and is open to XSS.
- The invitation `shrimpy://100.101.102.103:7447/K7Q2-9FXD`, which `shrimpy invite` prints for the owner's own machine, can't open in a browser and is plain HTTP. A phone's would be `https://<entry>/join#K7Q2-9FXD`, with the code typed in the installed app.
- `SameSite=Strict` (Chord) and `Lax` (p2) are untested with notification taps and installed launches. Android installed-app launches arrive `cross-site` with no cookies, and p2 lets them load as pages ([principals.ts](https://github.com/earendil-works/pi/blob/b22e525b325ff1934b4110f7fc60426fd6f0a8f3/apps/p2/src/hosts/principals.ts)). **(I)** Serve the app shell without a credential, and authenticate the socket.

## Claude Code and Codex in the client

The plan keeps Codex as a worker an agent delegates to ([7-on-its-own.md](../REDESIGN/design/7-on-its-own.md)), and has no Claude Code and no approvals that reach the owner. What follows holds only if the owner takes the [coding-agents note](coding-agents-scout-2026-11-11.md)'s proposal, where the protocols, sign-in and terms are.

- **(I)** Neither vendor's remote path admits another client: Remote Control serves Anthropic's apps, and Codex's remote access documents no third-party protocol. A Shrimpy client sees a Claude Code or Codex session when a Shrimpy agent drives it.
- Apps draw those sessions two ways: as a structured transcript from the Claude Agent SDK or Codex app-server (T3 Code, Craft Agents, CodexMonitor), or as a terminal running the CLI (Orca, Agent Orchestrator, Emdash). Those three have chat views too: Emdash's are ACP panels, Orca and Agent Orchestrator move one conversation between the two, and Agent Orchestrator never has both live at once.
- **(I)** The client would then need tool-call views fed by Shrimpy-owned shapes, so that a Codex worker's call and a Pi tool call draw the same way. It would need approval cards only if the contracts gain an approval request, and a terminal view only if raw CLI sessions are wanted. OpenChamber's terminal is built on T3 Code's browser adapter for libghostty-vt.
- **(I)** Such a session opens like any other session of the agent's, since the owner can open every session of every agent.
- In T3 Code a thread that a link starts is marked "From" the other machine ([remote access](https://github.com/pingdotgg/t3code/blob/HEAD/docs/user/remote-access.md)); how its agents drive threads there is in the [coding-agents note](coding-agents-scout-2026-11-11.md#prior-art-what-survived). **(I)** A session an agent drives should say which agent started it, from which thread. Starting one from the client means choosing the agent, its machine and the vendor; whose thread it becomes is a question in the [coding-agents note](coding-agents-scout-2026-11-11.md#for-the-owner).

## For the owner

1. **The wire.** Which wire the three programs and the web client speak, and whether the choice waits for p3's decision on Chord's app kit in the week of 2026-11-16, are the first two questions in [pi-agent.md](pi-agent.md#for-the-owner), which also has [the options](pi-agent.md#options-for-shrimpys-wire). For the web client: should the choice include the event-stream or long-poll fallback iOS may need, which is the plain HTTP entry the plan defers?
2. **Stack.** Should the web client be React, so it can take assistant-ui's runtime adapters, Streamdown and the behavior of AI Elements rather than build them? The look would come from your mockups, kept in one place, replacing shadcn/ui's styling. Whether AI Elements fit Shrimpy's own message shapes is unchecked.
3. **Desktop.** The plan has no desktop app beyond the web client laid out for a desk. Should a wrapper come when its tray, shortcuts or deep links are missed, and be Electron?
4. **Pages at the entry.** Should the gateway serve the web client at an address a phone reaches and let in pages from its own origin and listed wrappers, each device holding a session in a signed HttpOnly cookie whose hash the gateway keeps? Today the entry there refuses every page and serves no files. And should you be able to revoke one device, closing its sockets? Nothing yet takes a machine's token back at the gateway ([6-network.md](../REDESIGN/design/6-network.md)).
5. **The local page's session.** Should the page on the gateway's machine keep its session in an HttpOnly cookie, which other local ports also receive, or in a per-tab token, which page script can read?
6. **Phone invitations.** Should a phone join with the same eight-character code typed inside the installed app, through an `https://` join page in place of the `shrimpy://` link? The lines for a machine of yours are already [waiting on you](../REDESIGN/AUTHOR-TO-REVIEW.md); this adds a phone's.
7. **Certificates.** HTTPS where a phone comes in ends "None of Shrimpy's own for now" there, and [using-it.md](../REDESIGN/design/using-it.md) leaves how the gateway gets a certificate to settle. Should the entry only load a certificate and key from files, which an agent gets and renews with a skill, from `tailscale cert`, an ACME client using DNS-01 for your domain, mkcert or you? Or should the gateway run ACME itself?
8. **Who sends push.** Should the chat server send push, since it knows what was said and where you were last active, or the gateway, where your devices would sign in, though it never holds conversations?
9. **Long sessions.** A watch already shows a session's newest 200 items and how many came before ([using-it.md](../REDESIGN/design/using-it.md)). Should it page back from there itself, borrowing `ConversationTranscript`'s logic, or should the rule that contracts carry only Shrimpy-owned shapes bend for it?
10. **A hosted service.** Should the project run an optional relay? The plan's Not building list has a "mandatory hosting platform" ([PLAN.md](../REDESIGN/PLAN.md#order-of-work)), so it would serve only gateways that opt in, and the installed web app and Web Push work without it. Since a web view on iOS gets no Web Push, a companion app from the App Store needs one for push, as Home Assistant's does; one you build and sign could push with your own APNs key, which needs Apple's paid program. The plan's companion, which wraps the same pages, says neither. A phone outside the networks your machines share, without Tailscale, needs one too, unless the gateway is opened to the internet or put behind someone else's tunnel **(I)**. That tunnel, or a relay that carries your traffic, is a proxy in front of the gateway, which [6-network.md](../REDESIGN/design/6-network.md) says Shrimpy doesn't count on. If the project runs one, OpenChamber's Private Relay, which forwards sealed traffic it has no keys for, is the shape to copy **(I)**.

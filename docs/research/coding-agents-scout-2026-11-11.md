# 🦐 Coding Agents Scout

Originally researched: 2026-11-11
Status: Research; nothing adopted, installed or run

The question: how could the owner open a Claude Code or Codex session from Shrimpy's clients, and a Shrimpy agent drive one, and which code and terms bear on that? The plan has one of these: agents delegating to Codex, as [design 7](../REDESIGN/design/7-on-its-own.md)'s workers, built with helpers under Later. Claude Code is in the plan only as a comparison for the terminal's keys, and nothing in it has the owner open a Claude Code or Codex session from Shrimpy's clients.

Research agents read public docs, source and dated records on 2026-11-11, and a second pass rechecked 16 claims per topic against primary sources and corrected those that held only in part. Statements were read in the primary source linked here or under [Sources](#sources) unless marked **(I)** for the research's inference or **(S)** for a secondary source, such as a press report or a search summary.

Licenses are marked **copyable** or **study only** as in the [clients note](clients-scout-2026-11-11.md). Versions, stars, author counts and activity are as of 2026-11-11.

## Current recommendation

**If Shrimpy runs Claude Code and Codex sessions, run each as a child of the agent program that drives it, where that agent runs, through the vendor's own protocol: the Claude Agent SDK for Claude Code, and Codex app-server over stdio for Codex. Only Shrimpy's own session view and controls would cross the gateway (I).** Of the surfaces found, these two alone start, stream, steer, interrupt, approve, resume and list through documented calls **(I)**. T3 Code and Paseo use them. Below, a host is the code in the agent program that starts a vendor's session and speaks its protocol. For an agent's delegated jobs, the documented CLIs run detached are the plainer start **(I)**.

- **`shrimpy login` offers sign-ins today that may break their vendors' terms.** Anthropic's terms bar Pi's Anthropic subscription sign-in on a plain reading **(I)**, and Anthropic's Acceptable Use Policy, which names such services, takes effect on 2026-11-12. The two OpenAI subscriptions it offers weren't checked against OpenAI's terms. See item 1 in [For the owner](#for-the-owner).
- **The person's own login fits both vendors' terms when the vendor's own program uses it (I).** Anthropic doesn't prevent a person signing in to the unmodified `claude`, also where a product hosts it, and bars a third party from offering claude.ai login or holding its tokens. Its Agent SDK overview also bars offering claude.ai login or rate limits in products built on the SDK unless approved, which leaves a Shrimpy SDK host an open question ([below](#anthropic)). OpenAI lets local and open-source apps use the person's Codex login.
- **Nothing ready-made can run these sessions for Shrimpy (I).** pi-claude-code and pi-claude-bridge make Claude a model provider for Pi and host no session. Vercel's harnesses bring the `ai` framework and a network sandbox of their own, and TanStack's bring `@tanstack/ai` and one CLI run per turn, which can't steer. Borrow from them, T3 Code and Agent Orchestrator, and depend on none.
- **A host would end a running turn when its agent restarts (I).** That breaks design 7's promise that workers "Detach and outlive the caller", and design 1's and design 4's rules for an orderly restart.
- **ACP would suit the other agents, if the plan allows it (I).** ACP, the Agent Client Protocol, would let one client reach Gemini CLI, OpenCode, Cursor, Copilot and Kiro, and Pi through community adapters. The plan's Not building list names "ACP product": see item 9 in [For the owner](#for-the-owner).

What the research would do **(I)**:

1. Before the release, take the Anthropic subscription sign-in out of `shrimpy login` and refuse `sk-ant-oat` keys, if the owner agrees. It is the only step that touches today's code.
2. When the skill for coding delegation is rewritten with its feature, as [design 5](../REDESIGN/design/5-home.md)'s row on skills has it, base it on the documented CLIs run detached from the agent's shell (`codex exec`, `codex exec resume`, `claude -p --resume`), with `check_back`, the vendor's own sandbox and a structured outcome. A job then outlives an agent restart, as the Workers row promises. It brings three mismatches with the plan, all in item 3 of [For the owner](#for-the-owner):
   - the agent reads as idle while a job runs, and no client shows the job, which breaks [seeing work wherever it is](../REDESIGN/design/using-it.md), built on 2026-10-09 after the owner "did not see anything in the tui";
   - on Linux, a stop or restart of the installed service kills the job unless it runs in a systemd unit of its own ([below](#design-7s-codex-workflow-and-what-a-restart-does));
   - old Shrimpy's `shrimpy worker` commands don't come back and Claude joins as a backend, while the Workers row says renaming or removing worker commands or backends "needs review".
3. Run the app-server spike [below](#design-7s-codex-workflow-and-what-a-restart-does), and its Claude half, before building a host. For the Claude half, kill an SDK host mid-turn, then try `reinitialize()` through a custom spawner that keeps `claude` outside the agent program.
4. If the owner wants sessions they open from the clients, which the plan doesn't have, build them after the Codex workflow design 7 already plans.

Steps 2 to 4 belong with design 7's helpers and the retained Codex workflow, under Later in the plan's [order of work](../REDESIGN/PLAN.md#order-of-work).

## Claude Code's control surfaces

Of Claude Code's surfaces, only the Agent SDK documents every control **(I)**. It runs the unmodified Claude Code binary as a subprocess. A custom spawner can start it in a VM, in a container or on another machine.

| Surface | Start | Stream | Steer | Interrupt | Approve | Resume | List | Stability | License |
|---|---|---|---|---|---|---|---|---|---|
| Agent SDK | Yes | Yes | `streamInput()` | `interrupt()` | `canUseTool`, held as long as needed | By ID, or fork | `listSessions()` | Documented | TypeScript: custom, its use under Anthropic's Commercial Terms; study only, used as a dependency. Python: MIT; copyable |
| `claude -p`, stream-json | Yes | Yes | stream-json input | SIGINT | A hook or `--permission-prompt-tool` | `--resume <id>` | No | Documented; its control messages aren't | Custom; study only |
| `claude --bg`, agent view | Yes | No | No | `claude stop` | No | `--resume <id> --bg` | `claude agents --json` | Research preview since 2.1.139 | Custom; study only |
| Cross-session messaging | No | No | Posts text into a live session | No | No: a message "can't approve anything" | No | No | Documented, 2.1.224+ | Custom; study only |

- Steering, interrupting, and changing the permission mode or the model need the SDK's streaming input mode. `canUseTool` also answers `AskUserQuestion`, and "can stay pending indefinitely". A `PreToolUse` hook that returns `defer` lets the process exit and pick up later from the saved session.
- Since 2.1.302, `claude -p` starts in Manual mode, which denies a call that needs approval unless a hook or `--permission-prompt-tool` approves it. SIGTERM "leaves the turn that was in progress unfinished". `--bare`, which Anthropic says will become `-p`'s default, never reads a subscription login. No Anthropic doc found describes the two-way control messages (`control_request`, `can_use_tool`). They were seen in third-party code, such as Vibe Kanban's.
- Not interfaces: the transcript JSONL, whose format "changes between versions", and `~/.claude/jobs/`. `CLAUDE_CONFIG_DIR` with `CLAUDE_CODE_PROJECT_DIR_NAME` (2.1.234+) gives each embedded session its own place on disk.
- Remote Control serves only Anthropic's apps: claude.ai/code, the mobile apps and Claude Desktop. It polls Anthropic over outbound HTTPS, all its traffic passes through Anthropic, and it needs a subscription login: an API key, a `setup-token` token or a custom base URL won't start it.
- Channels (research preview) push events into a session and can relay permission prompts. Only plugins on Anthropic's allowlist load without a development flag.

## Codex's control surfaces

Codex app-server is the interface OpenAI's own apps use: JSON-RPC 2.0 over stdio by default, or over a Unix socket.

| Surface | Start | Stream | Steer | Interrupt | Approve | Resume | List | Stability | License |
|---|---|---|---|---|---|---|---|---|---|
| app-server | `thread/start`, `turn/start` | Notifications | `turn/steer` | `turn/interrupt` | Server requests | `thread/resume`, fork | `thread/list` | Experimental | Apache-2.0; copyable |
| `codex exec --json` | Yes | JSONL | No | A signal | Sandbox and policy flags only | `codex exec resume` | No | Stable | Apache-2.0; copyable |
| `codex queue`, `codex agents` | No | No | `codex queue` queues a message | No | No | No | `codex agents`, on a shared server | Stable | Apache-2.0; copyable |

- The stability signals conflict. The CLI reference labels `codex app-server` Experimental and for "local development or debugging", while OpenAI's Python SDK, released as Production/Stable, runs on it. Schemas are generated for each installed version, and no promise across versions was found. The TypeScript SDK spawns `codex exec`.
- The TCP WebSocket transport is "experimental and unsupported", and off loopback it takes unauthenticated connections by default during the rollout unless `--ws-auth` is set.
- `codex exec` is read-only by default and takes `--output-schema` for a structured final answer.
- OpenAI removed `codex mcp-server` and points to app-server. Its own apps reach another machine by starting app-server over SSH and relaying through OpenAI, with no protocol documented for anyone else.

## Terms on a person's own subscription

### Anthropic

What Anthropic's texts below allow Shrimpy **(I)**: the person's own unmodified `claude`, signed in by them with `claude auth login` where it runs, with Shrimpy never seeing the credential. Whether that holds when Shrimpy starts it through the Agent SDK is open (point 2 below). T3 Code, agent-deck and Conductor leave sign-in inside Claude Code the same way. agent-deck sends heavy unattended use to API keys or Team and Enterprise plans.

Anthropic's legal page for Claude Code, undated and read on 2026-11-11, says products, Agent SDK ones included, "should use API key authentication". Third-party developers may not offer Claude.ai login, route requests through Free, Pro, Max or Ultra credentials on behalf of their users, or "collect, store, or intermediate Claude.ai credentials or session tokens". Sign-in must finish in Anthropic's own flow, and enforcement may come without notice.

The same page doesn't prevent "an end user from signing in to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code". A platform that hosts it must be under Anthropic's Commercial Terms and run the binary unmodified, and may not pay for, resell or intermediate the person's usage: each user signs in with their own key or plan. Subscription limits "assume ordinary, individual usage". A product may say in plain text that it runs Claude Code. It may not use the name in a product, feature or company name, which bears on what Shrimpy calls the feature and its tools **(I)**.

Other texts that bear on it:

- The Agent SDK overview: no third-party claude.ai login or rate limits "Unless previously approved", agents built on the SDK included.
- The Consumer Terms, in effect since 2025-10-08: automated access only by API key or with explicit permission.
- The Acceptable Use Policy, announced 2026-10-08 and in effect from 2026-11-12: no unauthorized proxying, naming services that send traffic through consumer plans or disguise the calling client.
- The Help Center's article on logging in, updated in the week before 2026-11-11: third-party tools should prefer API keys, and Anthropic may let subscribers who turned on usage credits use some of them, billed to those credits. Tools that misrepresent themselves or push third-party traffic against subscription limits are prohibited.
- The Help Center, on 2026-06-15: Agent SDK, `claude -p` and third-party app usage "still draw from your subscription limits".
- API credits, since 2026-10-07: Max includes $100 a month, Ultra $200 and Team up to $500, pooled. They are spent through a linked Console organization's API keys. The [credits page](https://platform.claude.com/docs/en/about-claude/api-credits-for-subscribers) says they cover the Claude API and the Agent SDK, and not Claude Code. The Help Center's banner also names `claude -p` run with such a key, so whether a `claude -p` job draws on them is unsettled. Pro and Enterprise aren't eligible.
- `claude setup-token` makes a one-year subscription token for scripts and CI. It only makes model requests and can't start Remote Control.

Enforcement, from dated records:

- 2026-01-07: Crush dropped Claude Code at Anthropic's request.
- 2026-01-09: the API refused the subscription credential outside Claude Code. Pi's maintainer dropped and restored Pi's Anthropic sign-in, saying it risked bans.
- 2026-03-19: OpenCode removed its Anthropic sign-in over legal requests.
- 2026-04-04: third-party harnesses, apps that run their own agent loop on a Claude subscription, moved to extra usage, billed per token **(S)**.

**(I)** Three things stay open:

1. The June note keeps third-party apps on subscription limits, while the April reports moved harnesses to extra usage. One reading, unconfirmed: June means apps that run the official binary, and April means harnesses that replay its tokens. Armin Ronacher, a Pi maintainer, read the pause as covering only the Agent SDK, with the subscription still not permitted in other coding harnesses ([pi#5821](https://github.com/earendil-works/pi/issues/5821), 2026-06-16).
2. No text says whether a self-hosted app that starts the official binary for its one owner offers claude.ai login or rate limits in the SDK overview's sense. An SDK host on the person's login does give its sessions claude.ai rate limits.
3. No text says whether many unattended sessions an agent drives are "ordinary, individual usage". Anthropic's sales team is the documented place to ask.

### OpenAI

OpenAI's app-server docs say its authentication "has never been permitted for commercial or hosted services". A local or open-source app using it "can continue". OpenAI recommends Sign in with ChatGPT (SIWC), which covers "open-source and locally hosted apps"; a paid or remotely hosted app fills in an interest form. With SIWC the app sets `ACCESS_TOKEN` in app-server's environment, sends the name it registered under as `clientInfo.name`, and restarts app-server to refresh the token. Only Plus and Pro can grant an app their ChatGPT plan's usage, with weekly caps per app **(S)**.

**(I)** A self-hosted, MIT, single-owner Shrimpy fits "local or open-source", so the person's own `codex login`, the Codex binary's own sign-in, is allowed today.

`shrimpy login` also offers two OpenAI subscriptions through pi-ai, and neither was checked against OpenAI's terms:

- "OpenAI (ChatGPT subscription)" is SIWC, registered under the name "Pi", which pi-ai 1.0.0 hard-codes, so OpenAI is told Shrimpy is Pi **(I)**. As of 2026-11-11, upstream Pi lets `LoginOptions.agentName` change the name, so Shrimpy could sign in as itself only after an upgrade ([upstream Pi](pi-agent.md#upstream-after-100)).
- "OpenAI (ChatGPT Plus/Pro)" is Codex's legacy OAuth. In pi-ai 1.0.0 it signs in with a fixed client ID and `codex_cli_simplified_flow`, and sets `originator=pi`.

The owner signed their Linux machine's folder in to an OpenAI subscription through Shrimpy's sign-in on 2026-10-08, and an agent there runs on it ([STATUS.md](../REDESIGN/STATUS.md)).

## Sessions the person started elsewhere

Nothing in the plan has Shrimpy show sessions the person started outside it. What follows matters for attaching to the vendors' own servers.

### Codex: a background server to attach to

- `codex-app-server-daemon`, experimental, runs one detached `codex app-server` per `CODEX_HOME`, serving WebSocket on the Unix socket `$CODEX_HOME/app-server-control/app-server-control.sock`. The Codex TUI starts it, and the TUI, `codex agents`, `codex queue` and remote control from OpenAI's apps share it, in one environment.
- By default, an eligible daemon checks for updates after five minutes and then hourly, and an update restarts it after a grace period (`shutdownGraceSeconds`, 60 seconds by default, at most 300). After a restart it reloads its saved threads and aborts the running turn. For a local thread with its own config and an unchanged permission profile, it then tries one new turn to continue.
- The docs label only the TCP WebSocket unsupported, not the Unix socket, though app-server as a whole is experimental. `codex app-server` tags every thread `vscode`, which `thread/list` shows by default; only the standalone `codex-app-server` binary sets another source.
- **(I)** Attaching would make Shrimpy's Codex threads the person's own, visible and steerable in their Codex clients, and a turn would outlive an agent restart. It would also put the person's own Codex threads in an agent's reach, which nothing in the plan asks for. The costs: an experimental contract; a Codex login the agent can't have to itself; self-updates that can outdate the types Shrimpy generated, so Shrimpy checks the version at `initialize`; and an agent that depends on a socket and files outside it, which [design 6](../REDESIGN/design/6-network.md) rules out.
- **(I)** A private app-server per agent is isolated and pinned. On the person's `CODEX_HOME`, its threads would show in their Codex history, since `thread/list` shows `vscode` threads by default. A `CODEX_HOME` of Shrimpy's own avoids that.

### Claude Code: no server, only verbs and files

- Agent view runs background sessions under a local supervisor with no documented protocol. `claude agents --json` is "the supported way to read session state from outside Claude Code". The rest is CLI verbs: `--bg`, `--resume <id> --bg`, `stop`, `respawn`, and `attach` in a terminal. `--bg` refuses `-p`.
- SDK and `-p` sessions don't show on the agent view screen and are left out of `/resume`, but resume by ID. `listSessions()` and `getSessionMessages()` read all of the person's transcripts on that machine, interactive sessions included. A session resumes where its file is. On another machine it takes a `SessionStore`, a copy of its `.jsonl` in `~/.claude/projects/`, or a fresh session given the saved results.
- Cross-session messaging lets a script run by the same OS user post into a live session through `CLAUDE_CODE_MESSAGING_SOCKET` and a per-session token.
- **(I)** So an agent could list, read, start and resume Claude Code sessions from its shell with these verbs, and nudge a live one. Watching, steering or approving a live one takes `claude attach` or Anthropic's apps. Before resuming a session, check that it isn't live, as agent view does.
- **(I)** Remote Control could show Shrimpy's SDK sessions in the person's Claude apps. The SDK changelog fixes bugs in "SDK-hosted Remote Control sessions", but how a host turns it on wasn't found, and it needs a claude.ai login on that machine.

  - it gives a third-party agent loop claude.ai rate limits;

- **TanStack's** `ai-claude-code` runs one `claude -p` per turn with the prompt on stdin, so it can't steer. It defaults to `bypassPermissions` and answers an "ask" by denying, then running the turn again once the client approves. `ai-codex` runs `codex exec --experimental-json` with `approvalPolicy: never`. **(I)** They fit one-shot jobs in a sandbox.

## ACP, for the other agents

- ACP is JSON-RPC over stdio between a client and a coding agent. Its docs call remote agents "a work in progress". Zed and JetBrains govern it and are moving it toward a foundation. The spec is Apache-2.0, with no CLA. v1 is current (schema 1.31.0, 2026-11-10). In the v2 draft (2026-07-20), a prompt request returns when the agent accepts it.
- As of 2026-11-11, its registry lists 45 agents. Neither Claude Code nor Codex speaks it natively: `claude-agent-acp` wraps the Agent SDK and `codex-acp` starts app-server. Pi has only community `pi-acp` adapters. Upstream Pi has no ACP code and documents only ways to be driven: RPC mode with `RpcClient`, an SDK, and JSON and print modes.
- ACP's docs say an agent can itself be an ACP client of other agents.
- goose desktop (Apache-2.0; copyable; v1.59.0 on 2026-11-10) has ACP client code to borrow. Zed's is GPL-3.0-or-later; study only.
- **(I)** In front of Claude Code or Codex, ACP is one more adapter. It drops vendor detail, so it isn't worth adding just to control them. A client for the other agents waits on the owner's answer to item 9 in [For the owner](#for-the-owner).

**One agent driving others.** In T3 Code, agents on one machine start, message, wait on and stop threads on another. Its `delegate_task` runs work there, and the calling thread wakes with the result when it ends. Threads a link starts are marked "From" the other machine, and outside agents drive threads through T3 Code's own MCP server. In Orca one agent starts worker agents, and in AionUi a leader delegates to teammates. OpenRig (Apache-2.0; copyable) runs teams of Claude Code, Codex and Pi on tmux. pi-claude-bridge's `askclaude` add-on lets other Pi providers hand Claude Code tasks or questions; it wasn't read. **(I)** T3 Code's shape, where the result wakes the calling thread, is the one design 7's background helpers have.

Most of these apps are built around repositories and worktrees. Their adapters carry over to Shrimpy's agents and threads; their session model doesn't **(I)**. The [clients note](clients-scout-2026-11-11.md#apps-like-the-claude-and-codex-apps-ranked) weighs them as bases for Shrimpy's own clients.

## How it could fit Shrimpy

All of this section is the research's reading **(I)**.

**Where a session runs.** As a child of the agent program that drives it, where that agent runs: the SDK spawns `claude`, and app-server runs on stdio. Agents already run wherever it makes sense and reach the gateway with nothing inbound. So work on a machine with no agent needs an agent there, let in with `shrimpy invite` on the gateway's machine and `shrimpy login`, `shrimpy join` and `shrimpy up` where it will live. The vendor's protocol stays on that machine, so neither app-server's WebSocket nor Remote Control's relay is needed. The SDK's custom spawner, or app-server started over SSH, could reach a machine with no agent, at the cost of SSH access from the agent program.

**How it reaches the owner.** The agent builds the session view that clients draw ([design 2](../REDESIGN/design/2-contracts.md)), so it would turn Claude's or Codex's events into Shrimpy's shapes as it does Pi's, and no client would depend on a vendor's types. Clients reach it through the gateway as they reach any session. The vendor keeps the transcript, read through `getSessionMessages` or `thread/read`, so Shrimpy keeps no copy of its own. The session is then run and kept by the vendor and not by Pi, which the plan's direction doesn't allow for: see item 4 in [For the owner](#for-the-owner). Claude Code deletes transcripts after `cleanupPeriodDays`, 30 days by default, so the settings Shrimpy gives it would set that longer, or a thread loses its history after a month. How the gateway carries a session view is itself open, since Pi removed the client and server packages Shrimpy's wire uses ([upstream Pi](pi-agent.md#upstream-after-100)), and these sessions ride on whatever replaces them.

**How the owner sees it.** As a row of its agent's one list, marked working while it runs, which opens like any session. Agents that a Claude Code or Codex session starts of its own, such as Claude Code's subagents or those of Codex's multi-agent mode **(S)**, are its agent's work too, and show in that session's view. An approval or a question that waits on the owner would reach the phone as a Web Push to the installed web client ([clients note](clients-scout-2026-11-11.md#an-installed-web-app-with-web-push)). A job run detached from the agent's shell has no session, so it shows only where the agent reports it as work, which nothing does yet: until then the owner learns of it by asking the agent. Sharing a session with the vendors' apps would also put it on the phone through Anthropic's or OpenAI's relay, where the plan's [direction](../REDESIGN/PLAN.md#direction), decided on 2026-10-08, has the phone reached by Shrimpy's own client: see item 7 in [For the owner](#for-the-owner).

**The owner opens a Claude Code or Codex session from Shrimpy's clients.** It would be one session per thread: an Agent SDK session in streaming input mode, or a thread on the agent's own app-server.

| The owner | Claude Agent SDK | Codex app-server |
|---|---|---|
| Types while it runs | `streamInput` | `turn/start`, or `turn/steer` during a turn |
| Sends `/stop` | `interrupt()` | `turn/interrupt` |
| Answers an approval or a question | `canUseTool`, which waits as long as needed, with `defer` if the program must exit | Its server requests |
| Reads history | `getSessionMessages` | `thread/read` |

Every conversation is a thread in a channel. A session behind no thread opens for watching only, as the owner decided, so a session the owner types into would be a thread. Which thread is item 4 in [For the owner](#for-the-owner).

Another way needs no host: a terminal in the client running the person's own `claude` or `codex` where the agent runs, as Orca, Agent Orchestrator and Emdash draw these sessions. There, `claude attach` also reaches a background session. It is the plainest case of a person using the unmodified binary with their own login. Shrimpy then sees only a terminal: no events for the working mark, no approvals it can route and no transcript of its own. How apps move one conversation between a terminal and a chat view is in the [clients note](clients-scout-2026-11-11.md#claude-code-and-codex-in-the-client).

**A Shrimpy agent drives one.** The same hosts, given to the agent as tools: start, send or steer, wait, read, answer within a policy, interrupt and stop. Design 7 puts this with workers, apart from helpers. Seven tools and a policy are a mechanism, and an agent works from its instructions, a skill or its shell first. So they earn their place only where a skill over the CLIs can't reach: steering and answering a live turn. Their names and shapes, and the rule that "Claude Code" can't name a feature, go to the plan's [bucket for the agent's tools](../REDESIGN/PLAN.md#the-agents-tools-as-an-agent-meets-them). A bounded job needs no host: `codex exec --json --output-schema` and `codex exec resume`, or `claude -p --resume`, run from a skill and the agent's shell. For heavy Claude use, an API key is the documented route, kept where design 5 keeps keys: the folder's `providers/auth.json`, or a home's own.

Who answers a session's approvals is item 8 in [For the owner](#for-the-owner). [Design 3](../REDESIGN/design/3-identity.md) holds that a session or a tool selection isn't a permission boundary, and the agent already has a real shell with the same authority. So an approval sent to the owner would gate nothing the agent can't do itself.

**Sign-in.** For Claude Code, the person runs `claude auth login` where the agent runs, and Shrimpy never sees the credential. [Design 5](../REDESIGN/design/5-home.md) has one sign-in per Shrimpy folder that every agent started there uses, and [using it](../REDESIGN/design/using-it.md) keeps signing in to one command wherever agents run. So a login for each home would change both, and is item 5 in [For the owner](#for-the-owner). A `CLAUDE_CONFIG_DIR` under the folder's `providers/` would keep design 5, if Claude Code can keep the sign-in there apart from each home's sessions. Either way, the login isn't the person's own `~/.claude`, where the sessions they start themselves are kept. A command that starts the sign-in would come in a change of its own. A client may tell the person to run it, and never passes the credential. Codex is the same: one sign-in per folder, by `codex login` under a `CODEX_HOME` there with the same proviso, or a SIWC token from the folder's `providers/auth.json` handed to each agent's app-server as `ACCESS_TOKEN`.

## Design 7's Codex workflow, and what a restart does

**(I)** A host inside the agent program, the simplest route to live control, keeps neither design 7's Workers row nor what the plan promises Pi's own turns. An orderly stop gives "running turns a short timeout to finish, then pauses the rest" ([design 1](../REDESIGN/design/1-programs.md)). "Unfinished work resumes automatically", and an orderly restart never counts as a crash ([design 4](../REDESIGN/design/4-conversation.md)). A vendor turn ends with the agent either way, and at best its thread is resumed and a new turn asks it to go on. The plan has to say which it wants: see item 3 in [For the owner](#for-the-owner).

[Design 7](../REDESIGN/design/7-on-its-own.md) keeps workers as old Shrimpy had them: "Detach and outlive the caller", with Codex keeping "its real continue, send, wait and cancel protocol". It builds "the retained Codex workflow" and proves it "across caller disconnect and owner death". The design doesn't say who the owner is there, and this note reads it as the agent program that started the worker **(I)**. The row adds that "Renaming or removing worker commands or backends needs review", and the section's gate sends "a capability that can't be kept" back to experience decisions before removal. The [replacement map](../REDESIGN/history/from-old-shrimpy.md) puts "a focused adapter or skill for Codex" in place of old Shrimpy's worker supervisor, and says to "Delete the universal worker supervisor and backend state".

| Route | A running turn when the agent restarts | Live steer and approve | Cost |
|---|---|---|---|
| Detached `codex exec`, as old Shrimpy did | Runs on, waited on through its output files and never reattached; on Linux, a stop or restart of the service kills it (below) | No: continued only after it stops | No live view, and its agent reads as idle unless a durable task follows the job |
| app-server inside the agent program | Ends **(I)**; the thread resumes with `thread/resume` | Yes | Breaks the Workers row's promise |
| The person's Codex daemon | Runs on, if something outside Shrimpy's service started it, and is reattached with `thread/resume` **(I)**. Its own restarts, updates included, abort it | Yes, shared with the person's Codex clients | Experimental; one environment; updates itself by default. The agent depends on a process and files outside it, which design 6 rules out, so it couldn't run unchanged in a sandbox or on another machine |
| A long-lived app-server of Shrimpy's own, on a Unix socket | Runs on, on Linux only outside the service's unit **(I)** | Yes | A supervisor, as Agent Orchestrator's detached hosts are, which the replacement map deletes, unless each agent starts its own inside its own boundary. With SIWC, each token refresh restarts it and ends its turns **(I)** |
| Agent SDK inside the agent program | Likely ends **(I)**; the session resumes by ID | Yes | No source says what an SDK turn does when its host dies |
| `claude --bg` under Claude Code's supervisor | Runs on, if something outside Shrimpy's service started it **(I)** | No: CLI verbs and a terminal attach | Research preview. The agent depends on a process and files outside it, which design 6 rules out |

**(I)** On Linux, "runs on" holds only outside the installed service. The unit `shrimpy install` writes has `KillMode=mixed` ([systemd.ts](../../src/cli/service/systemd.ts)), and when the service stops, whatever is left in its cgroup is ended by force, detached or not. So a job, a daemon or a supervisor that an agent starts dies at every stop or restart of the service, `shrimpy install` run again and a crash of `up` included, unless it runs in a unit of its own, such as one `systemd-run --user` starts.

**(I)** A durable task that follows each detached job until it ends would show its agent as working, if it counted as the tasks that follow an input do ([design 4](../REDESIGN/design/4-conversation.md)). Design 7's Prove line already has "Pi task ownership never cancels detached external workers". The job's own output would still need a view, which the contracts don't have.

One lead for the spike: the SDK's `reinitialize()` reattaches "after a disconnect, so pending permission requests reach your `canUseTool` callback again". With a custom spawner that keeps Claude Code outside the agent program, a Claude turn might outlive its host **(I)**. Nothing has tried it.

Lessons from old Shrimpy's Codex worker ([runner.ts](../../shrimpy-old/src/workers/runner.ts)), examined on 2026-07-26, apply to every route **(I)**:

1. Take a delegated run's outcome (complete, blocked or failed) from a structured final report, such as Codex's `--output-schema` or a required final block, and never from its prose. Keep the end of the process or turn apart from the task's outcome. Old Shrimpy called a run blocked whenever "blocked" appeared in its first 1,000 characters.
2. One long-lived app-server per agent can host all its threads, so no job needs its own. Keep Codex's thread IDs beside Shrimpy's own records.
3. Run delegated work in a bounded sandbox by default. Full access, the approval policy and skipping the git check are named, explicit choices. Old Shrimpy wrote `danger-full-access` and `--skip-git-repo-check` into the transport. The sandbox is the coding agent's own, such as `codex exec --sandbox workspace-write` or Claude Code's permission modes, chosen in the skill: Shrimpy sandboxes no tool of its own.
4. Find the Codex binary even when a service's `PATH` misses it, probe its sign-in, record its version, and generate app-server types that match that version.
5. Spike app-server before building on it: two threads with interleaved events, a resume after the client restarts, one turn steered, another interrupted, and an approval answered from Shrimpy's policy.

For the stdio transport itself, the rules of GooeyPi (MIT; copyable) apply ([its RPC transport](https://github.com/am-will/gooey-pi/blob/cd5e0608f02d5d90058bc884a897e76e8caaa2c3/electron/main/agent-rpc/transport.ts) at `cd5e060`): split JSONL on LF only, so U+2028 and U+2029 survive inside strings; serialize writes under a byte budget with deadlines; and send TERM, then KILL, at shutdown.

## For the owner

Item 1 is about what Shrimpy ships today. It is a mismatch with the plan, and belongs on the [author's list](../REDESIGN/AUTHOR-TO-REVIEW.md): `shrimpy login` offers the Anthropic sign-in now, the release is close, and the Acceptable Use Policy it meets takes effect on 2026-11-12, the day after this note. Item 2 decides whether most of the rest matter, and item 3 comes before any host is built.

1. **The subscription sign-ins `shrimpy login` offers.** It lists "Anthropic (Claude Pro/Max)" first among its subscriptions, and `shrimpy login anthropic` offers it before the API key, with no notice ([sign-in.ts](../../src/agent/host/sign-in.ts)). The flow is pi-ai's ([pi-ai's Anthropic sign-in](pi-agent.md#pi-ais-anthropic-sign-in) has the client ID and the headers). It offers claude.ai login inside Shrimpy. It keeps the tokens in `providers/auth.json`, where every agent in the folder uses and renews them. It sends each request as Claude Code, under a code comment that says "Stealth mode". An `sk-ant-oat` key, such as one from `claude setup-token`, goes out the same way. Anthropic's API refused pi-ai 1.0.0's Claude Code version for `claude-fable-5-2` in reports of 2026-11-09 and 2026-11-10 on Pi's issue tracker.

   **(I)** Anthropic's terms ([above](#anthropic)) bar this sign-in on a plain reading, and the risk falls on the person's Claude account. Pi warns of extra-usage billing only in its coding agent's interactive mode, which Shrimpy doesn't use. Pi's maintainers say Anthropic recognizes Pi by its system prompt ([pi#5821](https://github.com/earendil-works/pi/issues/5821)), which Shrimpy's agents don't send. So their traffic either draws on subscription limits while posing as Claude Code or is billed per token as extra usage, and the person is told neither.

   The plan sends every subscription through Pi's flows ([design 5](../REDESIGN/design/5-home.md), [using it](../REDESIGN/design/using-it.md), the [setup skill](../../skills/shrimpy-setup/SKILL.md)), so this is a mismatch with the plan. The smallest fix is in Shrimpy's own code, around pi-ai:

   - leave the Anthropic subscription out of `sign-in.ts`;
   - refuse `sk-ant-oat` keys, and decide whether the runtime refuses those already in `auth.json`;
   - point subscribers to an API key and the monthly API credits that Max, Ultra and Team include.

   **(I)** A Claude subscription still serves through the person's own `claude`. pi-claude-code and pi-claude-bridge leave sign-in to Claude Code, but each is still a third-party agent loop on a subscription, so at most a labeled opt-in.

   The six other subscriptions `shrimpy login` offers weren't checked against their terms, and the OpenAI one the owner uses is among them ([above](#openai)).

   **Question:** take the Anthropic subscription sign-in out of `shrimpy login` and refuse `sk-ant-oat` keys, or keep it with a current pi-ai and a warning? A current pi-ai may mean moving Durable and Shrimpy's wire with it, since whether pi-ai 1.5.x runs under Durable 1.0.0 wasn't checked ([what upgrading `pi-durable` takes](pi-agent.md#what-upgrading-pi-durable-takes)). pi-ai 1.5.2 reports Claude Code 2.1.322 in place of the refused 2.1.280.
2. **Whether Shrimpy hosts these at all.** The plan keeps agents delegating to Codex, as design 7's workers, and nothing more. **Question:** should agents also drive Claude Code, and should the owner open Claude Code and Codex sessions from Shrimpy's clients? Items 5 and 6, and the thread in item 4, matter only after a yes.
3. **A running turn when its agent restarts.** Design 7's Workers row promises workers that outlive the caller. Its outcome has delegated work that "can be inspected from the CLI and clients" and "is honest about what a restart interrupted". Design 1 gives running turns "a short timeout to finish" at an orderly stop, and design 4 resumes unfinished work and never counts an orderly restart as a crash. A host inside the agent program, the simplest route to live control, would end a running turn when the agent restarts **(I)**. Nobody has tried it, and for the Agent SDK no source says what happens. Detached jobs run from a skill keep the Workers row's promise through an agent restart **(I)**, at three costs: the agent reads as idle and no client shows the job; on Linux, a stop or restart of the installed service kills the job; and old Shrimpy's worker commands don't come back, which the row says "needs review". The routes are in [the table above](#design-7s-codex-workflow-and-what-a-restart-does). **Question:** should the Workers row keep its promise, through detached jobs or an app-server outside the agent program? Or should it change, and for these sessions design 1's and design 4's rules for an orderly restart with it, so that a turn ends and is shown as interrupted? And may the worker commands go, with a skill over `codex exec` in their place, and Claude join Codex as a backend? **(I)** The research's lean: detached jobs for an agent's delegated work, and for a session the owner types into, a turn that ends and shows as interrupted.
4. **A session Pi doesn't run, and the thread it sits behind.** The plan has Pi own every session's "admission, queues, transcripts, task lifetimes, cancellation, compaction, recovery and committed observation", and leaves out "A second run queue, transcript, task manager, outcome journal or activity cache beside Pi's". A hosted Claude Code or Codex session has the vendor own each of those. A session the owner types into would also need a thread. It could be a thread in the owner's DM with the agent that runs it, with the vendor's session behind it in place of a Pi conversation, which is what the plan's [words](../REDESIGN/PLAN.md#words) say a session is. Or it could be a DM with the session as a member of its own. The words have a member be "A person or an agent", design 7 says helpers "never become agents", and of the [third kind of member](../REDESIGN/PLAN.md#a-member-that-is-neither-a-person-nor-an-agent) set aside in its early thinking the plan says "Neither has a home, a session or tools". So that would make a session a member, which the plan has nowhere. **Question:** may an agent keep sessions that Pi doesn't run, or does a Claude Code or Codex session stay work that a Pi session starts and follows, as design 7's workers are? If it may, which thread does a session the owner types into sit behind?
5. **Claude Code's sign-in: whose, and where.** Running the person's own unmodified `claude` fits Anthropic's legal page **(I)**. No text says whether Shrimpy starting it through the SDK counts as offering claude.ai login or rate limits in the SDK overview's sense, or whether unattended sessions an agent drives are "ordinary, individual usage". Two costs bear on the subscription. An open issue on Claude Code's tracker reports headless `claude -p` use drawing about 1.8 times as much of the 5-hour window as interactive use ([claude-code#97074](https://github.com/anthropics/claude-code/issues/97074)); pi-claude-code changed its entrypoint because of it, and one user's requests were then blocked as third-party, which the change's author couldn't reproduce ([issue #22](https://github.com/earendil-works/pi-claude-code/issues/22)). And `--bare`, which Anthropic says will become `-p`'s default, never reads a subscription login, so a skill's `claude -p` on the person's login may stop working then **(I)**. The SDK's documented way to name the app is `CLAUDE_AGENT_SDK_CLIENT_APP`, which puts the name in the User-Agent. Design 5 signs a Shrimpy folder in once for every agent started there, while Claude Code keeps its own login in `CLAUDE_CONFIG_DIR`. **Question:** should agents drive Claude Code on the person's subscription, or each on an API key, with the API credits that Max, Ultra and Team include where they apply (the Agent SDK, perhaps not `claude -p`)? And should a Claude Code login be one per Shrimpy folder, as providers are, or one per home?
6. **A proprietary dependency.** The Agent SDK's TypeScript package is proprietary, and its use is governed by Anthropic's Commercial Terms. The first dependency the new Shrimpy took beyond Pi's own packages, `cron-parser`, is a confirmed row of [design 7](../REDESIGN/design/7-on-its-own.md). `claude -p` with stream-json needs no package, though its control messages aren't documented. **Question:** may Shrimpy depend on the TypeScript SDK, or should it drive the person's installed `claude` with no package of Anthropic's?
7. **Shared with the vendors' apps, or private to each agent.** Attaching to the person's Codex daemon would put Shrimpy's Codex threads in their Codex clients (the TUI, `codex agents`, and OpenAI's desktop and mobile apps) and keep a turn through an agent restart **(I)**. That holds only if the daemon takes a client it doesn't know, which wasn't checked. It would also put the person's own Codex threads in the agent's reach, which nothing in the plan asks for. It would cost an experimental daemon that every client on the person's `CODEX_HOME` shares, and updates, on by default, that abort a running turn. It also breaks [design 6](../REDESIGN/design/6-network.md)'s rule that an agent shares nothing with the outside but the network. For Claude Code the counterpart would be Remote Control. It needs a claude.ai login on that machine, so a session on an API key (item 5) can't be shared this way, and no source says how an SDK host turns it on. Sharing would also put these sessions on the phone through Anthropic's or OpenAI's relay, and the plan's [direction](../REDESIGN/PLAN.md#direction) has the phone reached by Shrimpy's own client. **Question:** should the Claude Code and Codex sessions Shrimpy's agents run also show in Anthropic's and OpenAI's own clients?
8. **Approvals.** Claude Code and Codex stop to ask before some steps, and Shrimpy's contracts have no way for a session to ask a person to approve one. [Design 3](../REDESIGN/design/3-identity.md) holds that a session or a tool selection isn't a permission boundary. The plan gives agents a real shell and sandboxes a whole agent process or none ([direction](../REDESIGN/PLAN.md#direction)), so a sandbox for these sessions would be Claude Code's or Codex's own **(I)**. **Question:** does the agent that drives a session answer its approvals itself, as its real shell implies, with the person answering only in a session they type into; should the contracts gain an approval request the owner answers from any client; or should these sessions always run in Codex's or Claude Code's own bounded sandbox, which is close to the "Sandboxing for individual tools" the plan leaves out?
9. **ACP and the plan's Not building list,** which names "ACP product". **Question:** does an ACP client that lets agents drive other coding agents fall inside that line?

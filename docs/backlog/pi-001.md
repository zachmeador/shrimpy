# 🦐 PI-001: Contingency Pi Patch Branch Strategy

Status: todo
Priority: P2
Area: Pi Integration

## Why
[TUI-001](tui-001.md) still points at one architectural pressure: Shrimpy wants a coherent interactive UX, while Pi owns built-in slash command dispatch, `/settings`, autocomplete text, and visible `!` / `!!` bash affordances.

The preferred path for now is not a Pi fork and not a patch branch by default. Current Pi exposes the tool inspection, tool allowlist/denylist, tool override, `user_bash`, session naming, exact session-id, and extension command APIs needed for Shrimpy's core tool policy and additive TUI command work. Keep this note as a contingency ledger for the narrower case where Shrimpy needs upstream-shaped hooks for Pi-owned interactive UI behavior.

## Build
- Define the local Pi patch workflow around a separate upstream checkout only after a specific missing extension point is confirmed.
- Keep an upstream-tracking branch untouched and, if needed, a small `shrimpy-patches` branch for local changes.
- Add a repeatable update command or skill workflow only when the first patch exists: fetch upstream, rebase patches, build Pi, pack/install into Shrimpy for private development, then run Shrimpy tests.
- Track each Pi patch in a short ledger with base version, patch reason, touched files, and upstreaming status.
- Prefer additive Pi extension points over Shrimpy-specific behavior inside Pi.
- Decide the public-repo dependency story before release: upstream accepted hooks, a public fork dependency pinned to a commit, or a scoped fork package.

## Boundaries
- Do not vendor checked-in tarballs.
- Do not put Shrimpy product logic in the Pi fork.
- Do not fork the whole TUI as the first move.
- Do not make public Shrimpy depend on local path dependencies or unpacked tarballs.
- Do not carry compatibility shims for old fork paths once a cleaner upstream or public dependency path exists.

## Notes
- This is a contingency note, not approval to fork immediately.
- Do not use this as a dependency for [TOOLS-001](tools-001.md); Shrimpy can implement core tool policy through existing Pi APIs.
- Short-term private development can use local `npm pack` output from a separate Pi checkout.
- A private Pi checkout can diverge from upstream because it may contain local commits. For upstream testing, prefer an explicit upstream-tracking branch or detached `origin/main` checkout, and do not overwrite local work in that checkout.
- Current upstream packages publish under `@earendil-works/*`, not the older `@mariozechner/*` scope. A Shrimpy Pi bump should change imports and direct dependencies together.
- Current Pi `0.75.0+` requires Node `>=22.19.0`; Pi `0.74.2` is the `legacy-node20` rescue path for hosts that cannot upgrade Node yet.
- Pi-facing tool schemas now use `typebox` 1.x. If Shrimpy keeps `@sinclair/typebox` for config parsing, keep that boundary separate from Pi `ToolDefinition` schemas.
- Public release should use normal reproducible dependency sources: upstream Pi, a pinned GitHub fork commit, or a scoped npm package.
- Likely tracking doc: `docs/tracking/pi-fork.md`.
- Candidate patches should be narrowly framed as hooks/options, such as filtering built-in slash commands, adding custom settings sections, or hiding/disabling bash TUI affordances when shell is disabled.
- Related: [TUI-001](tui-001.md) defines how Shrimpy policy appears in interactive UX.

## Done
- The preferred Pi integration/update workflow is documented and runnable.
- Any local Pi patch has a ledger entry with reason and upstreaming status.
- Shrimpy can install and test against the patched Pi artifact in private development.
- The public dependency strategy is chosen before repo publication.
- No checked-in vendored Pi tarball is required.

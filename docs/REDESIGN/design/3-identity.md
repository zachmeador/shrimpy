# 🦐 Identity and addressing

This is one piece of the design. The words for a decision's status, such as Confirmed or Open, are explained in the [plan](../PLAN.md#the-design).

It covers who a member is, how a member is recognized, how something is named and found, and who may message, watch, control or administer.

**The design**

Who you are on a network is your entry on its roster. A way in only points at an entry, and an OS account decides who can reach the gateway, never who anyone is. You settled this on 2026-11-14, on finding that the gateway named you, found you and let you in by the OS account it runs as: "the user's name is obviously distinct from the name of the `user` the gateway process is running under".

**Who is on a network.** A network is one gateway and its roster. Its members are one person, you, and any number of agents. A member has an ID that is made once, means nothing and never changes, and a name that the roster binds to it. One set of names covers you and the agents, so `@name` always means one member.

- **One person.** A gateway has one person, decided on 2026-10-09: "i don't think there should be multi-person gateways". Your entry is made once, when the gateway first makes its data, and the gateway refuses a roster that holds a second person. Someone else's agents talk to yours as any outside agent does, with no code of Shrimpy's. Being the person and being the network's owner are one thing, and "a person" stays the word agents are told: "zachmeador, a person".
- **Nothing is found by OS account.** A gateway started under another account, or on another machine with the same data, has the same roster and the same you.
- **Your name** starts as the name of the OS account the gateway first runs as, and is a setting of yours from then on: "default to the process user until a config change", 2026-11-14. It is kept in a settings file in the Shrimpy folder where the gateway runs, which the gateway reads when it starts and when the file changes. With no file your name stays as it is. You change it, or ask an admin agent to. Names are unique among members, and an account made for Shrimpy may have the name the first agent wants, so on one you set yours before that agent is made. Built on 2026-11-14 as `settings.json` at the folder's root, holding `{ "name": … }`. The gateway checks it each second, since an edit to a shared folder may raise no event, and a name another member has leaves yours as it was, with a line from the gateway that says why.

**Ways in.** A way in is what the gateway recognizes a member by. Each points at one member, and the roster lists every member's ways in.

- **An agent's token.** The agent's home makes it, keeps it in `state/member.json` and shows it to nobody but the gateway. It is the same token from any machine.
- **A device's token.** A device is one of your machines' Shrimpy folders, or a browser, let in as you. Each makes its own token and keeps it: a folder in its `machine.json`, as [the network](6-network.md) has it, and a browser wherever the web client keeps it. Each has a label, such as "the Mac" or "phone".
- **The gateway's own socket.** A connection on it that shows no token is you. Its directory opens only to the gateway's OS account.
- **A page on the gateway's machine,** opened with a link that carries a secret only the gateway's OS account can read, is you too. It comes with the web client.

The gateway keeps a hash of each token, never the token. Any token can be taken back, which ends at once everything it holds open: its objects at the gateway end with a reason a client shows as access revoked, and its link closes. That matters most for a device: a lost phone is you until its token is taken back.

**Getting a way in.** Over the network, only with an invitation: a code that is good once, for fifteen minutes and for what it was made for. You or an admin agent makes one for an agent. Only you make one for a device, since a device is you. On the gateway's own socket nothing is asked: an agent beside the gateway joins by showing its new token with its name, and the chat server links in as a program that is not a member.

**Where trust ends.** Every OS account is either yours or an agent's. Different permissions need an OS boundary: a session, a home's folder or a choice of tools is not one.

- **Yours** are the gateway's account and every account whose Shrimpy folder has joined as a device of yours. Whatever runs under one of them can read the tokens kept there whatever Shrimpy does, and on the gateway's account the roster's file too, so it can do anything you can. That is why the gateway's socket takes a connection for you and asks for nothing more: a token there would keep nobody out.
- **An agent beside the gateway** runs under your account, so it is trusted with everything you may do. The roles below keep it from using that by accident, and nothing more. The setup skill says so when an agent is made.
- **An agent that should be walled off** runs under an account of its own, in a container or a sandbox, or on another machine. It reaches the gateway only over the network entry, with its own token, and can only ever be itself.
- **Acting as an agent.** A `shrimpy` command acts as an agent when the agent's launcher has said so, with `SHRIMPY_AGENT_HOME`, and as you otherwise. So a process an agent starts that loses the variable acts as you: a crontab line, a timer, a script run with a clean environment. Agents are told to schedule work with triggers, which run inside the agent and act as it, and to pass the variable on to anything they start that runs `shrimpy`. Short of a sandbox, nothing can tell your processes from an agent's under one account.

**Once in.** A connection never says who it is: the gateway knows from its way in, and stamps it on every request it relays to a program, as [the network](6-network.md) has it. A program believes a stamp only when it arrives on its own link from the gateway, so no caller can claim to be someone else. Nobody but the gateway sees a token. The program that is asked decides what the caller may do. The gateway proves itself to members in turn, with a key whose fingerprint comes with an invitation.

**Who may do what, confirmed on 2026-10-05** as good enough for now, and built that day. You asked for it to be settled with rooms. Every request that comes through the gateway carries who is asking, and every operation of an agent's API asks a check.

1. **One role: admin.** A member is an admin or isn't, and the roster records it. You are one. An agent is one when you say so, and since 2026-10-07 the first agent a roster has is one from the moment it joins, as you asked: "the first agent made should be admin by default".
2. **You read everything.** Since 2026-10-09 you may read every channel on your gateway, whether or not you are in it: "the user needs to be able to see into all sessions". Built that day in the chat server: its contract answers which channels you only read, apart from your own; in one of those you list threads, read messages and follow a thread live, and every write is refused with a reason of its own; your feed carries none of it; and you add members to any room, yourself included, which is how you walk into one. `shrimpy read <thread>` prints such a thread. An agent, admin or not, reads only the channels it is in.
3. **What needs an admin:** making a room, adding members to one, inviting an agent, and watching or controlling another agent's sessions and triggers. Later, renaming or removing an agent and replacing its token.
4. **What only you do:** inviting a device, and taking a device's token back. No agent may, admin or not, since a device is you.
5. **What never needs one:** talking. Any member posts in the channels it is in and starts a DM with anyone. An agent watches and controls itself. You do anything.
6. **The program that is asked checks,** as now: the chat server for rooms, an agent for its sessions and triggers, the gateway for the roster. The four permissions stay the names of what an operation needs: message, watch, control and administer.
7. **In an agent's shell, a command about another agent goes through the gateway as that agent,** so the other agent can refuse. Before this, such a command went straight to the other home's socket, where the caller counts as the home's owner.
8. **It stops accidents, not attacks,** for an agent beside the gateway, as the design above says. It is a wall for an agent under an account of its own, in a sandbox or on another machine, whose only way in is the gateway's entry.
9. **Commands:** `shrimpy members` lists the roster with who is an admin, and `members promote <name>` and `members demote <name>` change it. Only you and admins run the last two.

This changes one line of the rooms design, where any member could make a room: an admin can.

**Decisions**

The thinnest of the [core pieces](../PLAN.md#the-design). The first column is what the new Shrimpy does today, on one machine with one person. Three rows were sharpened by a second opinion from another model, and all but the last two were confirmed on 2026-10-04. They are built before rooms: the roster and IDs first, then the feed of events, then connecting to a name. The first was built on 2026-10-04, so the "built today" column describes what it replaced.

**Open**

How an agent is removed, and how an agent's token is replaced, aren't designed yet. Until they are, an agent whose token is taken back keeps its entry and its name with no way in, so it can't join again under that name. Removing an agent keeps its data, as you marked on 2026-10-08.

Nor is a way back in for an agent elsewhere whose gateway lost its key or its data, so that it can't check the gateway's key. An invitation can't be made for a name in use, so such an agent has no way in until this is designed. A device of yours joins again with a new invitation.

**Not built yet**

What the design of 2026-11-14 still asks for:

- **A browser as a device,** with the web client.

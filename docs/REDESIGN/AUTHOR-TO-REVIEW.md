# 🦐 For the Author to Review

What is waiting on you, and nothing else. The coordinator adds an item when a question needs you, or when a build makes a choice that changes the design. An item leaves when you answer it, and its decision moves into the [design](README.md). A small choice a build makes is noted in the [log](history/LOG.md) entry of the change that made it.

## Waiting on you

1. **The lines for a machine of your own.** `shrimpy invite` with no name, and `shrimpy join <link>` on the other machine, are built as you saw them on 2026-10-07, and [the network](design/6-network.md) has what each prints. You agreed to the way in as long as it was simple and clean, and haven't said yes or no to these lines: they are yours to change.
2. **An agent hearing a thread while it works in it.** Your idea of 2026-10-06: what anyone says in a thread reaches an agent that is working there at its next step, and wakes nobody. Pi has the piece for it, a submission that adds to a session and never starts a turn. [The proposal](proposals/hearing-a-thread.md) has how it would work, ten details with what I'd do about each, what it costs, and the version with no mechanism, which is one sentence in the instructions.
3. **`shrimpy up` starts an agent that ends again, alone.** On 2026-10-04 you confirmed that `up` stops everything it started when any one program ends, an agent included. You asked on 2026-10-07 that adding an agent take nobody starting anything, and I built more than that with it: with no agents named, `up` now starts an agent that ends again by itself, after a pause that grows while it keeps failing, and stops everything only when the gateway or the chat server ends. I said so before it was built, and you haven't said yes or no to that part. [The row](design/1-programs.md) has what it does.
4. **What a refusal is in Shrimpy's contracts.** Refusals carry their reason inside Pi's error code, and contracts still show Pi's own error types. Nothing is broken. Deciding it would make it intentional. Not urgent.
5. **Pi removed the packages Shrimpy's programs talk through.** Pi 1.2.0, on 2026-10-12, removed `pi-client`, `pi-server` and `pi-protocol`, and Chord 1.2.0 removed the service runtime Shrimpy's contracts are written in. The plan and the design still name them. Shrimpy installs today only because every Pi package it names is pinned at exactly 1.0.0. Moving `pi-durable` past 1.1.0 means a new wire for all three programs and their clients, and from 1.4.0 a one-way change to each home's storage. [The Pi note](../research/pi-agent.md#upstream-after-100) has what changed and three options for the wire with their costs, and [five questions](../research/pi-agent.md#for-the-owner): which wire, whether to wait for Earendil's decision on Chord's app kit in the week of 2026-11-16, whether the release ships on the 1.0.0 pins, when the plan says the packages are gone, and whether the choice reopens lockstep upgrades between machines.
6. **`shrimpy login` offers Anthropic's subscription sign-in.** It lists "Anthropic (Claude Pro/Max)" first among its subscriptions, as pi-ai offers it. An agent signed in that way is presented to Anthropic as Claude Code, in its system prompt and its requests, and nothing tells you. Anthropic's legal page for Claude Code says third-party developers may not offer Claude.ai login or route requests through a subscriber's credentials, and its Acceptable Use Policy, which names services that disguise the calling client, takes effect on 2026-11-12. Reports of 2026-11-09 and 2026-11-10 on Pi's tracker have Anthropic's API refusing pi-ai 1.0.0's Claude Code version for `claude-fable-5-2`. The six other subscriptions it offers, your OpenAI one among them, weren't checked against their vendors' terms. [The coding-agents note](../research/coding-agents-scout-2026-11-11.md#for-the-owner) has the details and the smallest fix: leave this sign-in out of `shrimpy login`, refuse `sk-ant-oat` keys, and point subscribers to an API key. Take it out before the release, or keep it with a current pi-ai and a warning?
7. **When the gateway's key is built.** You agreed on 2026-11-14 to [identity](design/3-identity.md) as it now stands. Its biggest piece of work is the gateway proving itself: a key whose fingerprint an invitation carries, and the network entry encrypted, as [the network](design/6-network.md) has it. Your own setup listens only on loopback and your tailnet, which already keep tokens off an open network, and the key would be built on whichever wire item 5 settles. Build it for the first release, or after it, with the docs saying until then that the entry belongs on loopback or a tailnet?
